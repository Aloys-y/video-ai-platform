# 长耗时视频任务消费改造方案

状态：首版实现与自动化验证已完成，部署记录见 [实施记录](kafka-long-task-consumer-implementation.md)。日期：2026-09-08。

## 1. 目标与保留项

将 Kafka 的消费循环与视频处理分离，视频长时间执行不再阻塞 poll。继续在结果和终态可靠保存后 ACK，不采用“提交内存线程池即 ACK”。

保留上传 OSS、任务与 Outbox、现有任务 Topic、视频准备链路、最多5个片段、共享片段池及 CountDownLatch。暂不新增片段 Topic、数据库任务扫描调度或工作流平台。

## 2. 推荐结构

```text
Kafka 任务 Topic
  ↓
Spring Kafka 消费容器（3个子消费者）
  ├─ 每个消费者最多1条在途消息
  ├─ 消息交给视频执行池后立即返回监听方法
  └─ 未ACK期间暂停交付新记录，仍持续poll
        ↓
视频执行池（3线程，有界提交）
  ↓ 取得数据库执行所有权
下载 → 转写 → 粗筛 → 裁剪最多5段
  ↓
共享片段池 → 模型调用 → 响应与片段结果保存
  ↓
视频父线程等待片段实际退出，保存整局终态
  ↓
完成协调器检查执行权和分配代次 → acknowledge()
  ↓
Spring容器提交安全offset，随后恢复交付
```

视频父线程和片段线程池独立。Kafka消费线程不能等待Latch、模型或工作池容量。原有TaskProcessor可以复用业务步骤，但不再由监听线程同步执行到结束。

## 3. 消费容器方案：先采用框架能力

首版使用 `AckMode.MANUAL + asyncAcks=true + max.poll.records=1 + enable.auto.commit=false`。每个子消费者最多持有一个未确认记录，3个消费者对应最多3个在途视频。

**暂停范围是一个子消费者负责的全部分区，不是只暂停当前消息所在分区。** 这是对前面逐分区设想的简化：直接利用Spring未完成ACK的暂停机制，降低乱序offset和自定义调度复杂度；接受同一消费者其他分区也暂缓交付的代价。

- 监听方法只登记在途记录、非阻塞提交、返回。
- 完成协调器通过Spring的Acknowledgment通知完成，实际KafkaConsumer操作交给容器；不在业务线程直接调用commit/pause/seek。
- 不能使用nack与asyncAcks组合，也不能仅给监听方法加@Async。
- asyncAcks不表示收到消息就提交，也不保证exactly-once；终态检查与写入幂等仍然必须实现。
- 核对项目实际Spring Kafka依赖版本并做嵌入式Kafka验证，不能仅依靠监听方法单元测试。

## 4. 容量与配置

| 项目 | 初始方案 | 说明 |
|---|---|---|
| Kafka消费者并发 | 3 | 保持当前规模 |
| 每次poll最多记录 | 1 | 一个子消费者一个在途视频 |
| 视频执行池 | 固定3线程，队列容量3 | 队列只容纳线程交接，业务在途总数仍限制为3 |
| 片段数 | 最多5 | 保留已落地的选择规则 |
| 片段线程池 | 本次不改 | 与消费解耦分开发布；当前正式入口仍为固定4/队列16 |
| max.poll.interval.ms | 候选5分钟 | 不再匹配视频时长；需覆盖消费协调及再均衡回调的最长阻塞，实测后启用 |
| pollTimeout | 候选1秒 | 暂停时同样持续poll；结合版本配置验证CPU占用 |
| 执行租约 | 候选90秒、每20秒续租 | 用数据库时间计算；独立续租线程，短SQL、有超时 |

即使正常情况下池容量足够，也要处理关闭/再均衡导致的提交拒绝：不得ACK或遗失消息。登记为待接管，仅保留有界记录，容量恢复后重试；无法安全恢复时由监督器停止并重建受影响容器，以未提交offset重投。不能无限在监听线程里重试入队。

容量许可在执行线程实际退出后释放，不能只看Future.cancel返回。无法退出的任务继续占用本地容量，防止不断创建新的“替代任务”。

## 5. 执行所有权与数据变更

实现时在 `analysis_task` 增加 `execution_owner`、`execution_lease_until`、`execution_heartbeat_at`。原因是执行权必须在下载前建立，而 `analysis_execution` 在下载并计算输入哈希后才创建。数据库仍只记录当前执行所有权，不作为任务扫描队列。

`retry_count/execution_no` 表示用户重试代次；`owner_token` 表示同一代次当前由哪个执行者负责。进程恢复或分区交接可以更换owner_token，不需要伪造一次用户重试。

1. 数据库短事务原子领取：任务为当前可执行代次，且执行权为空或租约已到期，才可设置新令牌。
2. 有效租约仍被别人持有：不ACK、不启动第二次AI调用，有限频率检查终态/租约；消费循环保持运行。
3. 续租、阶段更新、片段响应绑定、结果和终态写入必须校验owner_token、租约、任务代次及取消状态。
4. 不能“先查令牌，再无条件写”。子表写入应使用带条件SQL，或在短事务内锁定并验证执行行后完成写入。
5. 续租失败且无法确认有效执行权时停止发起新调用，关闭写入权限；新实例等租约过期后领取。
6. 所有权保护数据库绑定，不能撤销已发出的远端请求；UUID对象可能成为未绑定产物，后续按保留期清理。

全链路审计写路径，包括ASR提交占位、远端ID、产物绑定、片段开始/响应/结束及整局终态，不能只保护最后一次任务状态更新。

## 6. 完成、ACK和再均衡

在途记录包含消费者身份、topic/partition、任务消息、ownerToken、Acknowledgment和执行线程。首版以每次接收创建独立Slot对象、撤销标志及条件删除实现本地分配隔离，offset由Spring的Acknowledgment保存，不另维护一套提交账本。

- 全部成功、部分完成、明确失败或取消：对应终态可靠落库后才允许确认。
- 数据库写入失败：保留响应，不ACK；有限退避重试持久化。不能把提交失败重新解释成需要重做模型调用。
- 终态保存后ACK前崩溃：重投时检查终态，直接确认，不再分析。
- 分区撤销/丢失：立即使本地分配代次失效，关闭相关写入Scope、请求中断并停止续租；回调不能等待整局结束。
- 已撤销分配的完成通知不得调用旧Acknowledgment。对尚未提交的消息，由新消费者从数据库状态恢复。
- 分区重新分配后重建在途及暂停状态，不假设之前pause状态会保留。
- 旧线程可能不响应中断。它不能再写数据库；新实例仍可能遇到远端重复执行，需借助已保存请求ID/响应做恢复，不能承诺外部调用恰好一次。

异步工作线程的异常不会自动进入原来的监听器DefaultErrorHandler。新增完成协调器负责异步失败和持久化重试，监督器负责无法收敛的容器恢复，必须有告警，不能让未ACK记录永久挂住且无人处理。

## 7. 超时及结果语义

30分钟改为耗时提示，不能仅因排队超时将整局强制失败。单次下载、ASR、模型请求仍有超时；临时错误有限重试，保留总尝试次数和费用预算，用户可取消。

“等全部片段结束”包括成功、失败、取消，不是无限重试直到每个片段成功。

| 最终状态 | 定义 |
|---|---|
| COMPLETED | 所有选中片段均成功 |
| PARTIALLY_COMPLETED | 至少一个成功，其余已明确失败/停止且无待处理片段 |
| FAILED | 无可用结果且任务已结束 |
| CANCELLED | 用户取消，已成功结果继续可见 |

部分完成作为终态，需要同步更新枚举、状态机、SQL判断、前端轮询停止条件、结果展示及重试入口。空候选仍保留当前“未筛出候选”的范围说明，不伪造分析结果。

同时替换当前30分钟超时扫描和WorkerExecutionProperties对task-timeout/poll-interval的耦合校验。ExecutionBudget需区分任务取消/所有权失效与单次操作期限，不能简单把所有超时设置成极大值。停滞告警以阶段和单次操作期限判断，不把“长时间合法排队”误判为死锁。

## 8. 分阶段实施与验收

| 阶段 | 内容 | 必须通过的验证 |
|---|---|---|
| A | 租约与执行令牌、写路径保护 | 两执行者竞争只一人成功；旧令牌/取消/旧代次均不能写入 |
| B | asyncAcks、视频池、完成协调及再均衡 | 处理超过测试poll期限仍正常poll；终态前offset不前进；池满不丢消息 |
| C | 新超时语义、部分完成、恢复 | 部分成功可见；坏片段不会无限重试；重投复用已保存结果 |
| D | 故障注入与上线 | 实例强杀、主动再均衡、DB断连、提交失败、远端不响应中断均可追踪恢复 |

嵌入式Kafka测试要观察真实消费组和已提交offset，而不只是验证ack方法被调用。增加“一个子消费者分到多个分区”的测试，确认暂停范围与恢复时机。

指标至少包括：在途视频数、暂停时间、poll最大间隔、租约续租失败、旧令牌拒绝写入、未ACK终态、再均衡次数、片段等待时间与调用耗时、部分完成率。

发布采用停机切换：先停止接单并让旧同步Worker收尾，旧代码不支持令牌保护时不能与新Worker混跑。数据库先做兼容性新增；回滚前先停止新任务并处理在途执行，不能简单启动旧Worker接管租约中的任务。

## 9. 本轮不做

不新增分布式调度平台；不将ACK提前到内存提交；不同时上线弹性片段池参数；不把无限等待作为恢复策略。每个消费者一次一任务的吞吐/公平性限制先接受，后续有指标证明需要时再改为逐分区并发。
