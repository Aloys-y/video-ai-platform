# 队列容量对照压测（2026-09-08）

## 结论

在本轮已测的16/32/64中，建议保留16。扩大队列没有提升同时高峰吞吐，却延后了后来小任务的首次调用。不据此宣称16为全局最优；8等更小容量尚未对照。生产配置未修改。

## 方法

- 真实 SegmentAnalysisExecutor，4线程，请求间隔17ms；3/7/10分钟按1:60缩放为3/7/10秒。
- 同时高峰：3个父任务各12片段。大任务先到：30片段任务先提交，500ms后两个3片段任务到达。每组36片段。
- 每种场景/容量重复3次，轮换配置顺序，18组串行。总耗时19分22秒，共648个片段全部完成，无重复执行、无残留队列或活跃模拟调用。
- 模拟整局期限100秒（等效100分钟），特意放宽以避免30分钟生产期限干扰容量比较。没有云端调用、数据库写入或服务重启。

## 如何解释

- 容量16使先到大任务在入队时等待，后来父任务有机会提交；容量32/64可让大任务先排入几乎所有片段，小任务排在后面。
- 小任务首次调用等待中位数从约48秒降至29.53秒，约减少38%。这是本次模拟的观察，不是任务级公平保证。
- 按时间缩放对应，约29.5与48分钟的首次等待已触及或超过生产30分钟整局期限。因此保留16仅是这三种容量中相对更合适，不代表该峰值负载可以在生产期限内完成。
- 容量64最高只使用32个排队位置；本负载没有验证超过32的容量收益。

## CPU与内存限制

原始JSON记录每组进程CPU毫秒和每10ms采样的JVM已用堆峰值。它们包含测试框架、进度轮询和GC影响，不能用来直接计算单个队列元素内存，也不是RSS。饱和指标是遇到满队列的父任务数，不是每次拒绝重试次数。
