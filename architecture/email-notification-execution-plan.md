# 分析结束邮件通知：执行方案

日期：2026-09-13。状态：待实施，本文件不代表功能已上线。

后续决定：先实现无域名、无真实邮箱的 Mock 链路，见 [Mock 链路说明](email-notification-mock-validation.md)。下文邮箱绑定、提醒选项和真实 Provider 仍为后续计划。

## 1. 目标与取舍

用户提交视频后可以离开页面，在分析结束后通过邮件返回查看结果。通知属于非核心业务：允许极少量丢失，不影响分析成功、不自动重新调用模型。

- 保留数据库调度、租约、片段线程池与现有费用账本。
- Kafka 只传递“本次分析执行结束”事件，不承载视频分析任务。
- 不引入 Outbox、CDC、站内信中心、SSE、邮件附件或独立通知微服务。
- 不承诺邮件绝对不丢、不重；发送服务接受请求也不等于邮件最终进入收件箱。
- 默认关闭邮件提醒；验证邮箱后，由用户在提交时主动勾选。

## 2. 当前代码与接入位置

- `frontend/js/task-detail.js`：当前每 3 秒查询任务状态；保留该行为。
- `video-common/.../domain/User.java`：已有 email 字段，但不能将“字段非空”视为验证完成。
- `video-worker/.../scheduler/TaskDispatchRepository.java`：`finish()` 返回条件更新是否成功；`failExpired()` 逐条条件标记执行失败。
- `DatabaseTaskScheduler.Slot.run()`：当前调用 `finish()`，需要识别其返回值，失效执行者不得发送完成事件。
- API 的任务提交、重新分析入口：增加本次执行的邮件提醒选择；不接受客户端指定任意收件地址。

实施前补查所有终态写入点，包括正常失败、部分成功与租约过期；不得只覆盖正常成功。

## 3. 用户流程

1. 用户在账号设置填写邮箱，通过验证码验证。
2. 提交任务时，可勾选“分析结束后邮件通知”；未验证时给出绑定入口。
3. 成功、部分成功、失败均通知，每个执行代次最多建立一条逻辑邮件记录；主动取消不通知。
4. 重新分析时，在确认弹窗明确展示提醒选项，默认继承上次选择，允许关闭。
5. 邮件包含视频名称、结果状态和“查看分析结果”按钮。链接为配置的前端站点任务地址，仍需登录与归属校验。
6. 更换或解除邮箱后，不向旧地址发送排队中的邮件；改为跳过并记录原因，不自动转发到新地址。

无公网可访问的前端地址时，只能做本机功能验收；正式邮件不得使用 localhost 链接。

## 4. 链路与模块边界

```text
Worker 条件更新执行终态成功，提交数据库
  → 异步发布 video.analysis.finished.v1
  → Kafka 邮件消费组
  → 建立邮件发送记录，数据库提交后提交消费位点
  → API 内短周期发送器领取到期记录
  → 邮件服务
  → 更新发送结果，或安排有限重试
```

邮件消费者、发送器先部署在现有 API 进程中；开启功能后才启动。发送器是很小的重试组件，不复用视频调度器，也不复刻父子任务协调器。

采用“接收后落发送记录”而非消费线程睡眠重试：邮件服务故障时可以独立退避，不阻塞该分区后续事件，API 重启后也能恢复尚未发送的通知。

模块建议：

| 模块 | 内容 |
|---|---|
| video-common | AnalysisFinishedEvent，事件版本和状态定义 |
| video-infrastructure | Kafka 发布适配器、邮件 Provider 接口、发送记录 Mapper |
| video-worker | 正常结束与租约过期结束事件的发布接入 |
| video-api | 邮箱验证接口、通知偏好、事件消费者、有限重试发送器 |
| frontend | 邮箱验证表单、提交与重新分析提醒选项 |

## 5. 最小数据设计

### 用户与执行设置

- 用户增加 `email_verified_at` 与 `email_version`。修改邮箱立即撤销验证，并增加版本号。
- 任务保存当前执行的 `notify_email` 与 `notify_email_version`，重新分析时明确更新。
- 同一执行的偏好在发布前读取为快照；消费者不能拿新执行的偏好覆盖旧事件。
- 校验验证码后绑定邮箱必须检查版本，防止旧验证码验证新邮箱。

### mail_notification 表

| 字段 | 用途 |
|---|---|
| id、event_id | 主键；event_id 唯一 |
| task_id、execution_no、user_id | 业务归属 |
| email_version、recipient | 校验地址版本，实际发送时记录收件地址；日志脱敏 |
| payload | 模板所需最小快照，不存报告或密钥 |
| status | PENDING / SENDING / SENT / FAILED / UNKNOWN / SKIPPED |
| attempt_count、next_attempt_at | 有限重试 |
| claim_token、claim_until | 多 API 实例条件领取与宕机恢复 |
| provider_message_id、error_code、error_message | 排查与识别不确定结果 |
| created_at、updated_at | 时间 |

增加到期扫描索引 `(status, next_attempt_at)`。这是消费端发送记录，不是生产端 Outbox，无法弥补“数据库提交后、发 Kafka 前”宕机。

通知记录不进入 `ai_call_log`，邮件不是模型调用。

## 6. 事件与发布规则

一个 Topic：`video.analysis.finished.v1`。一个消费组：`video-mail-v1`。暂不创建统计消费组。

事件字段：`schemaVersion、eventId、taskId、executionNo、userId、status、finishedAt、taskName、notifyEmail、emailVersion`。

- Key 使用 taskId，eventId 使用稳定的 `taskId:executionNo:finished:v1`。
- 不携带邮箱验证码、完整报告、签名视频 URL、内部错误堆栈。
- `finish()` 或过期清理的单行条件更新成功才产生事件；更新失败不发布。
- 若终态更新使用显式事务，发布放在 afterCommit；禁止提交前发送。
- 通过独立小型有界发布执行器调用 `send()`，避免元数据获取等等待拖住视频线程或调度器；队列满记录并放弃提醒。
- 生产者开启幂等、`acks=all`，配置有限的投递超时和阻塞超时。最终失败回调记录 eventId 与安全错误，不在回调里 sleep 或无限补发。
- 第一版依赖生产者有限重试，不额外堆叠应用级发布重试队列。

Kafka 不可用、发布队列满、进程在提交后退出时，通知可能丢失；分析状态不回滚。页面仍可查询数据库结果。

开发环境可单 Broker、单分区；这种配置不具有副本容灾能力。正式副本数、ISR 与现有基础设施一起确认，不为演示伪装高可用。

## 7. 消费、幂等与发送重试

### 接收事件

验证版本和必要字段，忽略未开启提醒与取消事件。以 eventId 唯一键创建 PENDING 记录；重复键按已接收处理。数据库提交成功后再提交 Kafka 位点。

数据库故障不提交位点，通过容器退避重试；格式错误事件记录告警后跳过，不能永久堵住分区。应用侧 eventId 去重仍然必要，不能只依赖生产者幂等。

### 执行发送

- 初始发送并发 2，每 5 秒扫描到期记录，先获得本地容量再条件领取，不一次领取大量邮件排队。
- 初始领取期限 120 秒，邮件请求总超时最多 20 秒；领取期限须覆盖单次真实发送最大耗时。
- 发送前复查邮箱验证状态和版本、账号与任务有效性；不符则 SKIPPED。
- SENT 表示供应商已接受请求，不表示送达。回写必须携带 claim_token 条件，失效发送者不能覆盖新状态。
- 明确临时失败最多尝试 3 次（含首次），后两次延迟 1 分钟、5 分钟；不占用线程睡眠。尊重供应商 Retry-After，超过通知有效期则失败。
- 无效地址等永久错误直接 FAILED；首次排队超过 24 小时不再发送过时提醒。
- 若服务商支持幂等请求，用 eventId 作为幂等键；尝试之间保持相同请求内容。
- 超时、断连或 SENDING 领取过期时，可能已发送。优先按供应商能力查询或幂等重试；无法判定且无幂等支持则 UNKNOWN，不盲目补发以免反复打扰用户。

数据库记录不能独自实现外部邮件副作用的恰好一次。Provider 能力确认后再定最终超时分类，不能假设所有服务商支持幂等。

## 8. 邮箱验证与模板

- 建议接口：`POST /user/email/verification-code`、`POST /user/email/verify`；具体路径遵循现有账号模块。
- 验证码绑定用户、目标邮箱和版本，短期有效、一次使用；只保存摘要，限制错误次数。
- 可复用 Redis 保存临时验证状态与发送冷却：初始 60 秒冷却、每小时每用户与邮箱各 5 次，具体按邮件服务限制调整。
- 不恢复此前被关闭的全站粗粒度限流，只限制此类可对外发送邮件的入口。
- 验证邮件走受限的直接 Provider 调用，不依赖 Kafka，避免验证链路绕一圈异步通知。
- 标题示例：“你的视频分析已完成”；部分成功与失败使用不同文案。
- HTML 模板转义任务名，提供纯文本版本，结果链接由可信配置生成。
- SPF/DKIM 等发信域名配置按最终服务商要求落实；生产凭据不提交 Git。

## 9. 分阶段执行与验收

| 阶段 | 交付内容 | 必须通过的检查 |
|---|---|---|
| P0 配置与契约 | 确认服务商、发信域名、站点地址；事件 DTO、Provider 接口、功能开关 | Mock Provider 可运行；关闭开关不要求 Kafka/邮件服务可用 |
| P1 邮箱与偏好 | 用户字段、验证码接口、前端绑定与提交选项 | 未验证不可勾选；旧验证码失效；验证码错误次数/冷却；重新分析选项明确 |
| P2 事件发布 | Kafka 配置与终态发布接入 | 成功/部分成功/失败/租约过期覆盖；条件更新失败和事务回滚不发；Kafka 故障不影响任务完成 |
| P3 邮件消费 | 发送表、幂等消费、发送器、模板、有限重试 | 重复事件仅一条；落库后 ACK；临时/永久/不确定错误分类；重启恢复；失效领取回写失败 |
| P4 前后端联调 | 使用合成任务完成端到端流程 | 重试新代次独立通知；邮箱更换跳过；页面归属检查；费用记录无变化 |
| P5 部署验收 | 配置模板、README、数据库迁移与回滚说明 | 先 Mock 邮件验收；用户明确授权后才向指定测试邮箱实际发送 |

每个阶段完成即执行相关单元测试与集成测试，保存结果再进入下一阶段。全流程不要求重新分析真实视频，不产生模型调用。

重点故障用例：发布前进程退出（接受丢提示）；接收落库后 ACK 前退出（重复消费去重）；邮件已接受后回写前退出（幂等恢复或 UNKNOWN）；Broker/邮件服务不可用（视频正常完成）。

迁移遵循现有项目要求，先备份并确认无在途任务，不删除已有用户、任务或账本数据。功能开关默认关闭；回滚先停邮件发送器与消费者，再关闭发布，保留发送记录用于排查。
