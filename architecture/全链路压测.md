# 长耗时 AI 任务的可靠性设计与全链路压测

本文记录长耗时 AI 任务异步化的设计，以及如何通过全链路缩时压测确定 Kafka、Consumer 和 Outbox 参数。

这个业务的特点是：用户上传视频后发起 AI 分析，单次分析可能需要几分钟，极端情况下接近 30 分钟。如果在 HTTP 请求线程里同步执行，会占用 Web 线程、容易超时，而且服务重启后任务状态也难以恢复。

所以我把链路拆成：

```text
用户提交
 → API 创建任务
 → Outbox 记录待发送事件
 → Kafka
 → Worker 消费
 → AI 分析
 → 更新任务状态
```

## 一、为什么使用 Outbox

最初需要解决的是 MySQL 和 Kafka 的一致性问题。

如果代码是：

```java
@Transactional
public void createTask() {
    taskMapper.insert(task);
    kafkaTemplate.send(message);
}
```

`@Transactional` 只能控制 MySQL，不能把普通 Kafka 发送自动纳入同一个本地事务。

这里至少存在两个窗口：

- Kafka 发送成功，但 MySQL 最后提交失败：Kafka 中出现一个数据库里查不到的任务。
- MySQL 提交成功，但 Kafka 最终发送失败：数据库里任务一直是 `PENDING`，但 Worker 永远收不到。

Kafka 生产者重试只能解决“Kafka 发送过程中的瞬时网络故障”，不能解决“数据库提交和消息发送的原子性”。

因此我使用 Transactional Outbox：

```text
同一个 MySQL 事务：
  INSERT analysis_task
  INSERT task_outbox
COMMIT
```

任务和待发送事件要么同时存在，要么同时不存在。事务提交后，由调度器扫描 Outbox 并发送 Kafka。

这样系统允许消息重复，但不能丢任务，整体语义是：

```text
At-least-once 投递 + 消费端幂等
```

我没有宣称做到严格的 Exactly-once，因为 Kafka ACK 丢失、进程在发送成功后但更新 `SENT` 前崩溃，都可能导致消息重新发送。

## 二、为什么重复消息不会重复执行 AI

Kafka 消息使用 `taskId` 作为 key，相同任务会进入同一分区，因此可以保证同一个 key 在分区内的顺序。

但顺序性不能替代幂等。

例如：

```text
消息 A 第一次投递
消息 A 因 ACK 不确定再次投递
```

两条消息顺序完全正确，但仍然可能执行两次。

所以 Worker 开始处理前会做带条件的原子状态更新：

```sql
UPDATE analysis_task
SET status = 'PROCESSING'
WHERE task_id = ?
  AND status = 'PENDING'
  AND execution_no = ?
```

只有影响行数为 1 的 Consumer 才能真正调用 AI。重复消息、过期执行代次和并发消费者都会因为条件不满足而退出。

也就是说：

- `taskId` 分区解决顺序问题；
- 状态机原子更新解决重复执行问题；
- `executionNo` 防止用户手动重试后，旧消息覆盖新执行结果。

这三个机制解决的是不同问题。

## 三、长任务为什么会引起 Kafka rebalance

Worker 原来是同步消费：监听线程拿到消息后直接调用 AI。

Kafka Consumer 必须在 `max.poll.interval.ms` 内再次调用 `poll()`。如果 AI 处理 30 分钟，而配置只有默认的几分钟，Kafka 会认为这个 Consumer 已经失去响应，把它移出消费组并触发 rebalance。

需要注意，Consumer 仍然可能在发送心跳，但只要长时间没有 poll，依然会被移出消费组。

所以我做了两项配置：

```yaml
max-poll-records: 1
max.poll.interval.ms: 2400000 # 40分钟
```

一次只领取一个任务，避免一次 poll 拿到多条长任务后，后面的消息等待时间叠加；40 分钟则覆盖 30 分钟的 AI 上限，并给对象存储、数据库、网络抖动和 JVM 停顿留出约 10 分钟余量。

## 四、我没有只凭经验配参数，而是做了缩时全链路压测

为了避免真实调用大模型产生费用，我实现了一个只在 `loadtest` profile 生效的 Mock AI。

耗时分布是：

| 类型 | 比例 | 假设真实耗时 | 缩时耗时 |
|---|---:|---:|---:|
| 短任务 | 60% | 2～4 分钟 | 0.2～0.4 秒 |
| 中任务 | 30% | 8～12 分钟 | 0.8～1.2 秒 |
| 长任务 | 10% | 24～30 分钟 | 2.4～3 秒 |

整体按 600 倍缩短，相应地把测试环境的 `max.poll.interval.ms` 从 40 分钟缩小到 4 秒。

虽然 AI 是 Mock 的，但其他链路都是真实的：

```text
HTTP 并发请求
 → Spring 事务
 → 服务器 MySQL
 → Outbox 扫描
 → 真实 Kafka
 → Consumer Group
 → 状态机抢占
 → Mock AI 阻塞
 → 完成状态落库
```

前后两轮一共执行了 15 个场景、1255 条任务，全部进入 `COMPLETED`，对应 Outbox 全部进入 `SENT`，并确认日志中没有调用任何真实大模型。

## 五、压测暴露出的第一个问题：Kafka Topic 实际只有一个分区

代码期望有 6 个分区，但服务器上的 Topic 是之前自动创建的，实际上只有 1 个分区。

这意味着即使启动 3 个或 6 个 Consumer，真正工作的仍然只有一个，其余 Consumer 都处于空闲状态。

我后来用 `KafkaAdmin + NewTopic` 显式管理 Topic：

- Topic 不存在时按配置创建；
- 已存在但分区不足时扩容到配置值；
- 不再依赖 Broker 自动创建 Topic 的默认分区数。

扩到 6 分区后，同样配置下把 Consumer 从 3 增加到 6：

```text
吞吐：1.75/s → 3.22/s
Kafka 排队 p95：24.83s → 4.85s
```

说明 6 路消费在基础设施层面确实有效。

但生产默认我仍然配置为 3，因为 Mock 只能证明本系统能承载 6 路，不能证明模型供应商允许 6 路并发。真实并发还受供应商 QPS、账号额度和成本约束。

## 六、压测暴露出的第二个问题：Outbox 是同步逐条发送

原来的调度器逻辑类似：

```java
for (Outbox event : events) {
    kafkaTemplate.send(...).get(10, TimeUnit.SECONDS);
    markSent(event);
}
```

虽然每轮查询 50 条，但实际上是逐条等待 Kafka ACK。

因为 MySQL、Kafka 都在远程服务器上，每条消息还伴随多次数据库状态更新，所以批次里的消息产生明显队头阻塞。

实测发现：

- Batch 从 10 增加到 100，Outbox p95 从 52.19 秒降到约 27 秒；
- 但把扫描间隔从 3 秒缩短到 0.5 秒，Outbox p95 几乎没有变化。

这说明瓶颈不是“扫描得不够频繁”，而是“逐条等待 ACK”。

因此我把调度器改成了批量异步发送：

```text
扫描候选消息
 → CAS：NEW → SENDING
 → 异步发送 Kafka
 → Future 回调
    → 成功：SENT
    → 失败：退回 NEW，并设置下次可发送时间
```

同时设置：

```yaml
dispatch-batch-size: 50
dispatch-interval-ms: 1000
callback-threads: 10
send-timeout-ms: 10000
```

每轮用一条查询最多读取 50 条候选，不会一次把全部积压加载到 JVM；每条消息仍通过 CAS 抢占，避免多个调度器重复处理同一行。调度器不再逐条等待 ACK，而是让 Kafka Future 在回调线程中更新结果。Kafka 故障时，失败记录退回 `NEW` 并按 `available_at` 延迟重试；进程宕机留下的 `SENDING` 由恢复扫描重新接管。

同样是 100 条任务、0.5 秒扫描、6 个 Consumer：

```text
同步发送 Outbox p95：24.51s
异步发送 Outbox p95：11.80s
下降约 52%
```

异步后 Kafka 排队时间有所上升，说明消息更快地从 MySQL 转移到了 Kafka。这里由 Kafka 承担削峰填谷是预期行为；Consumer 的处理能力和 AI 并发额度通过 Kafka Lag 单独观察，不再用 Outbox 发送器按消费速度限流。

取消实验阶段的应用级在途计数后，我又补了突发和稳态对照，共 520 条任务，全部完成、Outbox 全部 `SENT`，没有触发发送重试或回调拒绝。

参数不是拍脑袋取的。相同 10 条/秒稳态下：

```text
Batch 50  Outbox p95：3.34s
Batch 100 Outbox p95：3.54s
```

批次翻倍没有收益，所以取更小的 50。原因是候选读取虽然是批量的，但 `NEW -> SENDING` 抢占和 ACK 后状态回写仍是逐条数据库操作；当前中间件跨网部署时，数据库 RTT 比查询条数更值得优化。

相同 3 条/秒稳态下：

```text
扫描 1000ms Outbox p95：1.38s
扫描  500ms Outbox p95：0.85s
```

500ms 只节省约 0.53 秒，却让空闲查询频率翻倍。相对于分钟级 AI 任务，1 秒扫描已满足当前投递 SLO，因此默认保留 `Batch=50、Interval=1s`。100 条突发时 p95 会升至 7.51～8.69 秒，但任务全部排空：ACK 前的积压留在 MySQL Outbox，ACK 后的积压交给 Kafka，这正是两层缓冲各自的职责。

## 七、如何验证 max.poll.interval 配置确实有效

我还专门做了一组错误配置实验。

安全配置是 4 秒，Mock 最长任务约 3 秒，没有出现 poll timeout。

然后我故意把它降低到 2 秒，运行 30 条任务，日志中出现了 4 次：

```text
consumer poll timeout has expired
```

Kafka 随后触发 rebalance，吞吐下降到 1.77 条/秒。

由于消费端有状态机原子抢占，30 条任务最终仍然全部完成，没有重复写入结果。但这个实验说明：幂等机制可以保证最终正确，不代表错误配置没有代价。Rebalance 仍然会带来停顿、重复投递和额外数据库压力。

## 八、最终参数结论

最终配置是：

```yaml
Kafka Partition: 6
单 Worker Consumer: 3
max.poll.records: 1
max.poll.interval.ms: 40 分钟

Outbox batch: 50
扫描间隔: 1 秒
回调线程: 10
SENDING 恢复扫描: 60 秒
```

这些参数不是所谓的“行业最佳值”，而是当前业务假设和测试环境下的起始值。

我的参数选择原则是：

- Batch 先按 `Batch / Interval >= 峰值创建速率` 估算，再取继续增大后 p95 无收益的最小值；
- 扫描间隔取满足投递延迟目标的最大值，避免频繁空查数据库；本轮 1 秒已满足 SLO；
- Consumer 数不超过分区数，并受真实模型 QPS 限制；
- `max.poll.interval.ms` 覆盖任务 p99 和安全余量；
- 分别观察最老 `NEW` 年龄和 Kafka lag，区分 Outbox 投递瓶颈与消费瓶颈。

生产环境下，当前“索引扫描 + 单条 CAS + 异步发送”足以支撑中低任务量。如果最老 `NEW` 年龄持续增长，先解决应用与 MySQL 的跨网 RTT，再考虑 `SELECT ... FOR UPDATE SKIP LOCKED` 或 owner/lease 方式的批量 claim，减少逐条往返并支持多 Dispatcher 实例。当轮询数据库本身成为负担时，才升级到 Debezium 一类 CDC；不应为了展示技术栈，在当前容量尚未需要时提前引入。

最后，我认为这部分项目的价值不只是“用了 Kafka 和 Outbox”，而是我通过故障模型和实测区分了三类问题：

```text
Outbox：解决数据库提交与消息发布的一致性
Kafka 分区：解决并行度和相同 taskId 的顺序
状态机原子更新：解决重复投递和并发执行
```

并且通过压测发现了“Topic 实际只有一个分区”和“同步等待 Kafka ACK”这两个仅看代码不容易发现的问题，再用对照实验验证了修改效果。
