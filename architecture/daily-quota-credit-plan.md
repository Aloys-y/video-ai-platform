# 每日免费额度与付费积分执行方案

状态：待实施。本文不修改运行中的计费行为。

## 1. 目标与范围

每位用户每天免费提交两次视频分析任务；免费额度用完后，用户明确确认使用积分，再创建任务。上传、查看结果、播放片段不收费。

第一版选择按任务固定积分报价，不采用按 Token 实时扣款，不增加任务预算、调用前余额检查等复杂机制。现有 ai_call_log 继续记录供应商真实成本，积分流水记录用户消费，两者用途不同，不互相替代。

先实现额度与积分闭环，再接真实充值。开发阶段仅使用管理员发放的测试积分；上线真实付费必须完成支付接入，不能把测试积分功能称为已支持充值。

## 2. 推荐业务规则

以下为实施默认建议，积分价格、视频限制与补偿规则需在上线前最终确认。

| 项目 | 规则 |
| --- | --- |
| 每日免费 | 每个账号每天 2 次；Asia/Shanghai 自然日，不累计 |
| 免费扣除时机 | 成功创建任务时占用，上传不占用 |
| 付费价格 | 每任务固定 P 积分，可配置；P 尚未确定，不默认绑定人民币 |
| 扣费方式 | 创建任务时直接扣除；无需冻结钱包和完工结算 |
| 优先级 | 优先免费，用完后必须经用户确认积分报价 |
| 视频规模 | 免费和付费先采用同一时长上限、最多 8 个片段；单片段无时长上限时还需限制送入模型的总片段时长 |
| 规模校验 | 前端读取时长用于提示，Worker 使用 FFprobe 核验；超限在 ASR 前结束并退还权益 |
| 视频上限建议 | 第一版候选值 30 分钟；总片段时长上限及价格依据已有成本记录确定，不能直接当作已确定产品规则 |
| 无交战片段 | 正常完成筛选服务，不视为故障、不自动退款；提交前说明 |
| 部分成功 | 保留结果，可免费补跑失败片段 1 次，不重复跑已成功片段 |
| 整局失败 | 自动退回该次免费额度或积分；已退款任务再次执行必须重新获取权益 |
| 补跑后仍部分成功 | 保留已完成服务，不自动整单退款；不再无限免费重试，必要时管理员补偿 |
| 用户取消 | 未领取时取消可退；开始执行后主动取消不自动退。与平台故障区分 |
| 已成功任务重分析 | 当前接口不支持，本期不新增；以后按新任务计费 |

跨日退款：免费次数退回原占用日期，不转为今天的额外次数；积分退款不受日期影响。历史已退回次数仅用于核对，不允许重新领取昨天的额度。

免费次数仅是账号级额度，不能防止批量注册。第一版沿用认证、增加提交频率限制；公开推广前补邮箱验证和注册防滥用措施，不引入复杂设备风控。

## 3. 与现有代码的衔接

- UploadService.submitTask 当前通过事务创建任务，并使用 uploadId 粒度的 Redis 锁防并发重复提交。额度扣除必须加入同一个 MySQL 事务；Redis 锁不能作为积分正确性的唯一保障。
- TaskService.retryTask 当前只允许 FAILED/PARTIAL 并递增执行代次。改为先检查原收费记录：可免费补跑的 PARTIAL 消耗补跑资格；已退款 FAILED 重新报价、重新获取权益。
- Worker 继续使用现有数据库调度、租约、执行代次和条件写入。只有当前有效执行者成功更新终态后才能触发补偿判断，过期执行者不能退款。
- ai_call_log 不增用户余额字段，不从供应商 Token 明细反推应扣积分。任务详情将“本次消耗积分”与“模型调用成本”分开展示。
- LoadTestController、TestController 等测试入口在生产环境禁用，避免绕过收费服务创建真实任务。

## 4. 最小数据结构

新增四张表，不引入 Outbox、Kafka、Redis 额度缓存或冻结账户。

### user_daily_quota

字段：user_id、quota_date、used_count、updated_at。唯一键 (user_id, quota_date)。

使用服务端统一业务日期。先幂等创建当天行，再执行 used_count < 2 的条件递增。退款条件递减且不能低于 0。无需定时清零。

### credit_account

字段：user_id（唯一）、balance、updated_at。积分用 BIGINT 整数，禁止浮点计算。扣款使用 balance >= amount 的条件更新，更新 0 行返回余额不足。

### task_charge

字段：id、task_id、execution_no、user_id、request_key、request_hash、source(FREE/CREDIT)、quota_date、points、price_version、status(CHARGED/REFUNDED)、free_retry_used、parent_charge_id、created_at、refunded_at、refund_reason。

唯一键：(user_id, request_key)、(task_id, execution_no)。request_hash 防止同一幂等键被用于不同提交参数。免费补跑记录关联原收费单，退款后的再次付费执行生成新收费单，不覆盖历史。

FREE 记录即免费额度的审计凭证，无需再创建免费次数流水表。

### credit_ledger

字段：id、user_id、delta、balance_after、type(GRANT/CONSUME/REFUND)、business_key、task_charge_id、operator_id、reason、created_at。

business_key 唯一，分别使用发放单号、收费单扣款编号、收费单退款编号。钱包更新和流水写入同事务，禁止直接改余额而不记流水。

任务删除不能级联删除收费记录和积分流水。对测试历史任务不追溯扣款，也不为没有收费记录的任务退款；上线前确认无在途任务。

## 5. 提交与并发控制

1. 前端查询账户概览和提交报价，显示“免费分析（今日剩余 N 次）”或“使用 P 积分分析”。报价接口只读、不占额度。
2. 提交携带 requestKey、所确认的支付方式及 priceVersion。双击和请求重试使用同一个 requestKey。
3. 服务端鉴权、校验上传归属和参数，再进入事务。按统一顺序获取用户计费锁（credit_account 行，即使免费用户也创建零余额账户），串行处理同一用户的计费操作。
4. 查询 requestKey：已成功直接返回原 taskId；参数不同则拒绝复用。
5. 根据最新额度重新判断。客户端原本确认免费、但额度已被其他请求用完时，返回重新确认，绝不能静默扣积分。价格变化同样要求确认。
6. 条件扣免费次数或积分，创建任务、收费记录及必要的积分流水，统一提交。
7. 任一步失败全部回滚。事务提交但响应丢失时，客户端用原 requestKey 重试得到同一任务。

同一 uploadId 的既有去重逻辑需与 requestKey 统一：先确定是否已创建任务，再扣款，不能重复付费后返回旧任务。唯一键冲突要回滚整个事务，再在新事务查询原结果；不能捕获异常后继续提交部分扣款。

不同用户不共享计费锁；事务只做短 SQL 操作，不包含文件下载或模型调用。

## 6. 失败补偿与恢复

任务终态和计费补偿可能分两步完成，不能只依赖 finally 或进程内回调。

- 终态持久化后，调用统一补偿服务；收费状态 CHARGED → REFUNDED、权益退回、积分退款流水必须同事务。
- 增加低频补偿扫描：分页查找“符合退款条件的任务终态＋未退款收费单”，补齐进程宕机中断的退款。
- 补偿根据 task_id＋execution_no 匹配，不按 task_id 模糊退款；免费补跑的父子收费关系也要校验。
- 人工重试前，在同一事务中解决原执行的未完成补偿，再创建新执行；避免重试改变任务状态后扫描遗漏历史失败。
- 多 Worker 同时补偿由收费行锁、状态条件更新和唯一业务键保证只退一次。
- PARTIAL 免费补跑的资格使用条件更新；并发重试只允许一次成功。免费补跑如果没有新增成功结果，不能错误地退还已提供的原任务服务。
- 租约过期导致平台失败时允许按产品规则退款；底层供应商可能仍收费，成本继续留在 ai_call_log，由平台承担，不自动重放调用。

## 7. 接口和前端

建议接口（最终按项目路由规范落地）：

- GET /billing/summary：当天免费额度、积分余额、时区、价格版本。
- GET /billing/ledger：分页查询本人积分流水。
- POST /billing/quote：校验上传归属，返回免费或积分报价；不收费。
- 扩展 /upload/submit 和 /task/{taskId}/retry：幂等键、报价确认字段；返回任务 ID 与实际使用的权益类型。
- 管理员积分发放接口：权限检查、正整数上限、发放业务单号和操作原因；客户端不能自行调用充值成功逻辑。

界面变化：

- 导航用户区域展示“今日免费 1/2 · 积分 120”，手机端放账户菜单，避免导航拥挤。
- 上传确认页显示时长限制、免费或积分报价、失败和无交战规则。超出额度时不在用户不知情的情况下提交。
- 提交中禁用按钮；网络超时不生成新幂等键。
- 任务详情展示“免费任务 / 已扣 P 积分 / 已退回”，费用页保留原成本账本。
- 免费补跑按钮明确显示“免费重试失败片段（剩余 1 次）”；已退款后重新提交明确显示新的报价。
- 全部新增文案提供中英版本；充值未接入时不展示可完成真实付款的虚假入口。

## 8. 分阶段实施与验收

### P0：规则与迁移

确定 P、视频及总片段时长上限、PARTIAL 补跑和取消规则。完成 SQL、实体、唯一键及索引，备份测试库。检查所有创建任务入口。

验收：空库初始化及现有测试库迁移均成功；无配置时生产不意外开启扣款。

### P1：额度、积分、幂等提交

实现 BillingService、账户查询、测试积分发放、报价与提交事务。保留现有调度逻辑。

验收（真实隔离 MySQL，不只 Mockito）：并发提交免费最多成功两次；余额不变负数；同一幂等键只创建一单；事务插入失败不扣钱；免费报价失效不静默扣积分；跨日按服务器时区统计。

### P2：退款与补跑

接入终态补偿、低频扫描、退款后重试重新计费、PARTIAL 一次免费补跑。校验 owner/代次失效执行不会触发旧账退款。

验收：重复退款只生效一次；跨日退款归原日期；终态后宕机可补偿；补偿与重试并发不重复退扣；部分成功复用结果不重收；失败补跑不可无限执行。

### P3：前端闭环

账户额度、提交确认、余额不足、流水和任务收费标记；中英文及移动端适配。

验收：两次免费后显示付费确认；未确认不扣；刷新和双击不重扣；积分、人民币成本不会混淆。使用 Mock 模型端到端，不调用付费模型。

### P4：真实支付（单独立项）

选择支付渠道后新增充值订单。服务端定价，校验支付通知签名、订单归属、金额、币种及状态；以支付单号幂等入账。不能以浏览器跳回成功页作为到账依据。补充订单查询和对账，退款/撤销规则独立设计。

验收通过渠道沙箱，再小额真实验收；真实资金操作单独确认。P4 完成后才开放公开充值。

## 9. 上线与回退

先后台测试账号验证，再小范围启用。观察免费使用量、付费任务数、退款数、补偿积压、每任务真实成本；据此决定固定价格是否覆盖成本。

上线前暂停接单并确认无在途任务，备份数据库。回退时关闭新付费提交入口，保留账户查询和退款补偿；不得删表、清流水或把已扣款任务重新扣一次。

每阶段完成后记录改动和验收结果，再推进下一阶段。当前仅输出方案，不开通支付、不调整用户余额、不扣真实费用。
