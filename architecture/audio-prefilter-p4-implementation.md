## 执行流程

```text
父线程读取 OSS 冻结片段清单，核对执行快照
→ 短事务准备 analysis_segment 记录
→ 识别同代次已成功结果、已保存的模型响应
→ 依次提交全部片段到实例共享有界线程池，满队列时持续等待，受整局期限约束
→ 工作线程限速、生成片段签名 URL、调用视频模型
→ 原始文本/结束原因/请求 ID/用量保存 OSS
→ 数据库先保存响应引用，再校验 JSON 和证据时间
→ 独立短事务保存片段结果
→ 父线程通过 CountDownLatch 等待，定期收集成功结果、回调进度
→ 全部成功后按原片时间排序，返回给后续汇总
```

父线程不进入片段池。工作线程不 ACK、不完成父任务、不触发汇总。视频模型通过片段 OSS 签名 URL 读取视频，不把片段转为 Java 内存中的大字节数组。

## 主要入口

- `SegmentAnalysisService.analyze(taskId, executionNo, deadline, progress)`：同步等待整个片段阶段，只在全部成功后返回结果。deadline 由父流程传入，不能为每个片段重新计算一份完整任务期限。
- `SegmentAnalysisExecutor.execute(...)`：共享有界池、等待容量后提交、CountDownLatch 完成统计及取消收尾；不再限制每视频在途数量。
- `SegmentPersistenceService`：每次状态或结果写入使用 `REQUIRES_NEW` 短事务，5 秒事务期限，不跨事务等待模型。
- `DashScopeVideoProvider.callDetailed(...)`：返回正文、实际用量、请求 ID 和结束原因；旧 `call(...)` 接口保留。
- `SegmentModelSettings`：将视频模型、采样率、输出上限、提示词和连接配置加入不可变执行快照。

调用示意：

```java
var result = segmentAnalysisService.analyze(taskId, executionNo, taskDeadline,
        progress -> { /* 父线程接收已成功数、预期数及已完成片段用量 */ });
// 只有正常返回才可把 result.reviews() 交给汇总服务。
// P5 再负责整局终态持久化和 Kafka ACK。
```

## 默认参数

| 配置 `analysis.segments` | 默认值 | 含义 |
|---|---:|---|
| threads | 4 | 每个 Worker 实例的工作线程上限 |
| queue-capacity | 16 | 实例共享等待队列长度，待压测起点 |
| request-interval-ms | 1000 | 本片段池请求启动的最小间隔 |
| cancellation-grace-ms | 2000 | 取消后额外等待线程退出的时间 |
| max-response-bytes | 1048576 | 允许保存的单片段响应大小 |

队列拒绝使用 `AbortPolicy`，正常满队列时父线程持续重试当前片段，不跳过它，也不停止后续片段；不再设置独立入队超时。等待期间检查整局截止时间、任务取消、执行代次及线程池关闭。`stats()` 提供活动数、队列长度、完成数和 `saturatedBatches`（遇到过拥堵的批次数，每批只计一次，不代表失败），首次遇到拥堵记录 debug 日志。父任务状态约每 250ms 检查一次。

容量估算为 `线程数 × 目标排队时间 ÷ 单段耗时`。16 的起点假设是 4 线程、单段约 30 秒、目标排队约 120 秒；这不是已测得的服务保证。已有两个 5 秒样本耗时约 9.9/21.1 秒，尚不足以代表长片段。当前最多 3 个 Kafka 父消费者、每视频最多 100 片段，不尝试一次缓存全部 300 个任务；超出队列的提交在父线程等待。接受大任务先占队列、小任务等待更久的取舍，P7 按长片段耗时分布和账户配额调整参数。移除旧 `per-video-concurrency` 与 `admission-timeout-ms` 配置。容量估算中的 120 秒只是计算假设，不是入队或队列等待的硬截止时间。整局默认从 PROCESSING 开始最多 30 分钟，Kafka 未领取期间不计入；当前 max.poll.interval.ms 为 40 分钟，单次模型请求仍有自身超时。

每批 Latch 计数等于本次需要执行的片段数，复用结果不计入。任务正常/异常退出在 finally 扣减；未提交和排队取消在协调线程扣减，通过 Job 同步状态保证只扣一次。父线程每 20ms 限时 await 并扫描已完成结果，保留串行进度回调，不再通过完成队列控制补交。Latch 归零仅表示收尾完成，仍需检查每项结果才能汇总。

这些是实例限额，不包含旧整片路径，也不覆盖其他 Worker 或同账户其他应用；账户级限额、并发 1/2 对照仍在 P7 验收。

## 失败、取消和恢复

- 普通片段失败不阻止后续提交或同批排队工作；在剩余总期限内处理其他片段，保留成功结果，全部收尾后整局失败，不生成残缺的完整报告。
- 正常队列拥堵不会将剩余片段标记未提交。只有取消、总期限耗尽、线程池关闭或协调异常导致退出时，当前及剩余未提交项登记 NOT_SUBMITTED 并完成计数，排队项移除并计数，在途调用尽力中断并有界等待实际退出。BatchFailure 包含逐项状态快照（index 对应本次 work 列表）；数据库中的未启动片段保持 PREPARED，父任务保存失败原因，不伪装为模型执行失败。
- 取消、父代次变化、总超时或进度回调失败：关闭本批写入入口、移除排队工作、尝试中断在途工作，有界等待实际退出。
- `BatchFailure.converged()` 区分线程已退出和仍占用线程；不会用 `Future.cancel()` 的返回值假装远端调用已停止。未退出的调用仍占实例线程额度，迟到结果不得经已关闭入口写入。
- 数据库条件更新同时核对父任务仍为 PROCESSING 且 executionNo 匹配。关闭入口前已进入的短事务会先结束；本地关闭不会回滚已经提交的结果。
- 同代次 SUCCEEDED 直接读取；PROCESSING 且已保存响应只重新解析；PROCESSING 且无响应不自动重发。明确失败通过任务级新代次重试，跨代次引用由 P5 接入已有严格复用接口。
- 每条片段记录的 `usage_json` 保存响应 OSS 引用和 `reportedUsage`。实际用量未知保持 null，不以零替代；失败后的已知用量也保留。金额结算和父任务费用展示在 P5/P6 接入，工程预留不等于厂商账单。
