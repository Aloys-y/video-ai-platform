# 视频分析任务迁移：数据库 + 后台调度器

> 已由 `database-task-scheduler-lightweight-plan.md` 替代。用户已明确不要求历史兼容，新方案移除双后端切换、分析 Outbox 和通用自动恢复调度设计；本文仅保留为历史讨论记录，不作为实施依据。

日期：2026-09-10
状态：详细设计讨论稿，尚未实施。本文以当前源码为依据，不代表运行中的服务已切换。

## 1. 决策与范围

将视频分析任务的派发机制从 Kafka 改为 MySQL 任务表驱动。API 提交任务后快速返回，Worker 根据本地可用容量原子领取任务，完成后直接更新任务终态。

主要理由：业务并发不高，任务耗时长；数据库已经保存任务状态、执行代次、租约和片段结果。移除 Kafka 消费位点、分区暂停、重平衡及 ACK 与数据库状态之间的协调，可降低实现和运维成本。

本次不重写视频分析流水线，不引入新的分布式调度平台，不把每个片段改成独立调度任务，不重新讨论滑动窗口或替换 CountDownLatch。

目标不是“恰好调用模型一次”，而是：任务不会因进程内派发失败而失去恢复入口；同一时刻数据库只认可一个有效执行者；旧执行者不能写入当前结果；已保存响应优先复用。

## 2. 当前代码与迁移对应关系

| 当前组件或机制 | 迁移处理 |
|---|---|
| UploadService 创建分析任务，同时创建执行 Outbox | 数据库模式下只创建任务及必要业务记录，保持事务与额度规则 |
| TaskService.retryTask 增加代次并创建 Outbox | 增加业务代次、重置状态和调度字段，不投递执行消息 |
| LoadTestTaskService | 同步适配数据库入口，避免压测走旧链路 |
| TaskConsumer、AsyncVideoCoordinator | 用数据库调度器和视频执行器替代消费协调职责 |
| AsyncConsumerSupervisor、KafkaListenerConfig、DeadLetterConsumer | 数据库模式下不创建或不启动 |
| TaskLeaseService、ExecutionOwnership、受保护写入 | 保留并扩展领取与恢复需要的条件 |
| TaskProcessor | 保留分析业务；移除 KafkaTemplate 强依赖和消息式返回语义 |
| AudioPrefilterPipeline、SegmentAnalysisService、SegmentAnalysisExecutor | 复用，重点验证所有权传播和取消收尾 |
| OutboxDispatcherScheduler、OutboxRecoveryScheduler | 数据库模式下停止分析任务派发和恢复；检查是否还有其他业务用途 |
| Redis 缓存 | 保留，但不能用缓存判断是否可领取任务 |
| 分析任务完成事件 | 核实实际订阅方，不能直接遗漏 TaskProcessor.sendTaskEvent |

代码中的业务代次为 analysis_task.retry_count；领取身份为 execution_owner。二者不是同一个概念：进程故障后的恢复通常保持业务代次，重新生成 owner。

## 3. 目标架构

```text
前端上传 → 对象存储
用户确认 → API 本地事务创建 analysis_task → 返回 taskId
                              ↓
               Worker 数据库调度器定期扫描
                              ↓
                预留本地容量 → 原子领取
                              ↓
                    视频业务线程池
             下载 → ASR → 文本筛选 → 裁剪
                              ↓
                   共享有界片段分析池
                 模型重试 → 响应/结果保存
                              ↓
                 父任务终态持久化与缓存更新

独立租约维护：登记的有效执行 → 续租 / 取消检查
恢复入口：未领取任务、领取过期任务、持久化待核对任务
```

任务表既是展示状态的来源，也是调度的持久化依据。无需再发送一次消息使已经提交的数据库任务“生效”。进程内唤醒可作为以后优化，不作为正确性依赖。

## 4. 状态与字段

### 4.1 保留业务状态机

```text
PENDING → QUEUED → PROCESSING
                      ↓
        COMPLETED / PARTIALLY_COMPLETED / FAILED

取消 → CANCELLED
用户重试失败/部分完成任务 → PENDING，retry_count + 1
```

- PENDING：事务已提交，等待数据库调度器领取。
- QUEUED：已领取，正在交给本地视频执行器；不再表示“已经进入 Kafka”。
- PROCESSING：当前业务代次已开始，可能正在执行，也可能等待故障恢复。
- 自动接管 PROCESSING 不回退到 PENDING，也不自动增加 retry_count。
- 历史 DEAD 状态兼容保留，不再产生 Kafka 死信语义。
- 对外处理阶段继续复用现有字段，前端不必感知派发机制变化。

### 4.2 复用与新增字段

复用：task_id、status、retry_count、execution_owner、execution_lease_until、execution_heartbeat_at、started_at 及现有业务字段。

建议新增：

| 字段 | 建议类型 | 用途 |
|---|---|---|
| dispatch_backend | VARCHAR(16) | DATABASE / KAFKA，过渡期明确任务归属 |
| next_dispatch_at | DATETIME(3) | 下次允许领取的数据库时间；避免恢复失败后热循环 |
| recovery_count | INT NOT NULL DEFAULT 0 | 当前业务代次自动恢复累计次数，不混用 retry_count |
| dispatch_hold | TINYINT NOT NULL DEFAULT 0 | 调度隔离标记；结果未知或恢复预算耗尽时停止自动领取 |
| dispatch_error_code | VARCHAR(64) NULL | 固定、脱敏的调度错误分类，便于定位 |

dispatch_hold 不替代业务状态：已能确认失败时写入现有失败/部分完成状态；暂时不能安全确认终态时保留记录并隔离告警。隔离任务必须在任务详情或管理查询中可见，不能无提示地显示为正常处理中。

手动重试重置 recovery_count、dispatch_hold、next_dispatch_at 和调度错误；清理旧执行权并增加业务代次，仍复用现有授权与可重试状态校验。

建议索引起点：

```text
(dispatch_backend, dispatch_hold, status, next_dispatch_at, task_id)
(dispatch_backend, dispatch_hold, status, execution_lease_until, task_id)
```

这只是候选索引。迁移实现时核对字段类型、现有索引和实际 EXPLAIN；不能承诺一个带 OR 的大查询靠索引就一定高效。初始表和增量迁移脚本必须同步维护，不能只修改 Docker 初始化 SQL。

## 5. 调度与原子领取

### 5.1 按本地容量领取

初始视频并发继续为 3，每个 Worker 独立控制；通过 Semaphore 或等价容量许可预留执行位置，而不是读取 activeCount 后计算空闲数。activeCount 是瞬时观测值，不能承担并发正确性。

领取顺序：

1. 非阻塞申请一个本地视频容量许可；没有许可立即结束本轮。
2. 从数据库获取小批候选任务；候选查询不代表领取成功。
3. 条件 UPDATE 竞争一个候选，只有更新一行才算领取成功。
4. 提交视频业务池；任务退出或提交失败时恰好释放一次本地许可。
5. 没有领到任务也立即归还许可。

视频池保留很小的有界队列作为任务退出与许可释放交接的缓冲，但许可覆盖已领取、已提交、正在执行的全部视频，不能以队列容量扩大领取数量。避免父任务占用片段池线程再等待其子任务。

### 5.2 第一版使用条件 UPDATE，复用现有租约模式

当前 TaskLeaseService.claim 已经采用原子条件更新。第一版沿用该方向，不必立刻引入批量 SKIP LOCKED 领取。

候选按 next_dispatch_at、创建时间、task_id 稳定排序。为新任务与过期恢复任务分别查询，每轮交替优先顺序，避免长期只处理其中一类；只取小批候选并在竞争失败后有限尝试，避免忙循环。

示意领取 SQL（字段名与完整条件以最终 Mapper 为准）：

```sql
UPDATE analysis_task
SET execution_owner = :newOwner,
    execution_lease_until = TIMESTAMPADD(SECOND, 90, NOW(3)),
    execution_heartbeat_at = NOW(3),
    status = CASE WHEN status = 'PENDING' THEN 'QUEUED' ELSE status END
WHERE task_id = :taskId
  AND retry_count = :expectedExecutionNo
  AND dispatch_backend = 'DATABASE'
  AND dispatch_hold = 0
  AND next_dispatch_at <= NOW(3)
  AND status IN ('PENDING', 'QUEUED', 'PROCESSING')
  AND (execution_owner IS NULL OR execution_lease_until <= NOW(3));
```

两个 Worker 查到同一个候选没有问题：原子 UPDATE 决定胜者。领取不依赖 Redis 锁，也不使用 JVM 锁实现跨实例互斥。

候选快照可能在查询后改变，因此执行前还要核对 owner、代次、状态；所有真正业务写入继续使用数据库所有权保护。领取事务只处理短 SQL，不包含线程等待、下载或模型调用。

### 5.3 调度异常必须闭环

| 故障点 | 行为 |
|---|---|
| 扫描数据库失败 | 本轮退出、记录指标，下一轮重试；不能误标任务 FAILED |
| 领取竞争失败 | 尝试下一个候选；无候选时归还许可 |
| 领取提交结果未知 | 不启动业务、不凭猜测重试付费调用；按 owner 核对，无法核对则等待租约到期 |
| 领取成功但线程池拒绝 | 按 owner 条件释放领取并设置短退避；释放失败则等待租约过期恢复 |
| 领取成功后进程立即崩溃 | 数据库仍保留任务；新进程在租约过期后恢复领取 |
| 任务执行返回但终态未保存 | 按恢复规则延期再领取，不能当作完成 |

失败清理只能释放自己生成的 owner，不能无条件清空他人的租约。定时方法最外层捕获异常，防止一次未捕获异常导致周期任务永久停止。

## 6. 租约、取消与写入保护

沿用当前初始值：租约 90 秒、续租固定延迟 20 秒。定时维护与耗时业务使用不同线程池；数据库查询设短超时，续租优先于普通健康日志。数据库时间判断租约有效性，本地单调时间用于保守的令牌到期检查。

领取成功后尽快登记有效执行，避免租约无人维护；登记和提交之间发生错误时必须注销与释放。若本地任务不启动，不应无限续租，应触发派发异常处理。

续租要求任务代次、owner 和未过期租约均匹配。一次续租异常或更新行数不为一，继续采用当前保守策略：使本地 token 失效，请求业务线程停止，并禁止新模型调用和受保护写入。

保留 TaskLeaseService.fenced：在短事务内锁定父任务行、校验执行权，再执行实际 Mapper 写入；只做“先查询再在另一个事务更新”会重新引入检查与写入间隙。

维护线程只负责续租/检查/发出中断，不替业务线程释放其本地容量。容量必须到实际业务退出时才释放；如果片段尚未真正退出，登记收尾并隔离该本地执行，不可因 Future 已取消就假设资源已释放。

用户取消：API 更新 CANCELLED 并使执行资格失效；本地定期检查和片段 scope 检查使正在等待的工作退出，启动前的片段移出队列，成功结果按照现有规则保留。旧 owner 不能把 CANCELLED 改回成功。

## 7. 故障恢复不是重新跑一遍

恢复前读取数据库及已保存的阶段产物，按状态决定是否能安全继续：

| 记录状态 | 恢复策略 |
|---|---|
| QUEUED，尚未开始业务 | 同代次重新领取并启动 |
| 下载/本地临时文件丢失 | 重新准备本地文件；复用已存在的可验证对象存储产物 |
| ASR 已有云端请求标识 | 优先查询或复用现有结果；不能盲目重新提交 |
| ASR/文本请求是否执行未知 | 使用对应阶段已有恢复判断；不具备证据时隔离或明确失败待人工重试 |
| 冻结的候选清单、裁剪产物已存在 | 校验清单及配置后复用 |
| 片段 SUCCEEDED | 复用结果，不重复调用 |
| 片段 PROCESSING 且已绑定原始响应 | 重新解析/保存，不重新调用模型 |
| 片段 PROCESSING 但无响应 | 结果未知，不自动重新发送付费请求 |
| 原 DIRECT_VIDEO 模式处于未知调用状态 | 保留当前禁止恢复自动重发的策略 |
| 父任务已终态，缓存更新失败 | 修复缓存，不重新分析 |

新增轻量 TaskRecoveryPolicy 汇总恢复决策，复用各阶段已有逻辑。它不应通过仅检查 started_at 就认定付费调用失败。

恢复预算建议起点：可恢复协调失败最多自动恢复 5 次，间隔 5、15、30、60、120 秒并加入抖动；recovery_count 持久化，进程重启不能重置预算。领取后业务从未启动的派发拒绝单独短退避，不混为模型失败。

恢复预算耗尽或结果未知：能明确写业务终态时使用现有失败/部分完成规则；否则设置 dispatch_hold=1 和固定错误码，停止自动领取并告警，保留后续核对入口。数据库不可用时无法持久化隔离标记，先停止本地执行，等数据库恢复后再核对。

片段内部 429/5xx 重试继续由 SegmentAnalysisService 管理，与调度层恢复分开计数。调度层不能把所有异常都变成重试整个视频。

## 8. 组件建议与执行接口

```text
DatabaseTaskScheduler
  定期触发、容量许可、候选公平性、有限领取

TaskClaimRepository
  候选查询、CAS领取、归属检查、延迟释放/隔离

VideoTaskRunner
  业务池、执行登记、所有权绑定、实际收尾与许可释放

TaskLeaseService
  续租、释放、数据库受保护写入（复用）

TaskRecoveryPolicy
  区分终态、可恢复、结果未知、需隔离

TaskProcessor
  视频业务执行（复用主体）
```

第一版组件保持轻量，不再造复杂调度框架。可将领取 SQL 保留在现有租约服务中，避免无意义的接口层级。

TaskProcessor 的输入改为与 Kafka 无关的 TaskExecutionRequest(taskId, executionNo)，其余业务信息从数据库读取。返回结构化执行结果或抛出明确的未收尾异常，不再用 boolean 表达“可以 ACK”。

必须核查处理器中依赖旧任务对象状态的判断：领取将 PENDING 变成 QUEUED 后，startProcessing 仍应正确执行；恢复 PROCESSING 不能重复开始未知的直传模型调用。

## 9. API、事件与配置

API 创建和手动重试维持现有鉴权、事务、额度与缓存一致性。新增任务调度归属和 next_dispatch_at 应在同一创建事务中确定。缓存不得在事务回滚后留下成功状态。

TaskProcessor 当前调用 sendTaskEvent，移除 KafkaTemplate 前查清事件订阅方：

- 若前端只查询数据库/缓存，完成通知可由现有查询流程承担。
- 若确有必要的订阅方，先提供本地事件或其他明确交付机制，不能默默删除。
- 主任务终态已经持久化后，通知或缓存失败不得反向触发模型重新分析。

建议配置：

```yaml
videoai:
  dispatch:
    backend: database
    scan-delay-ms: 1000
    candidate-batch-size: 12
    video-concurrency: 3
    lease-seconds: 90
    renewal-delay-seconds: 20
    max-recoveries: 5
```

全部为起点参数，领取数仍受许可限制，candidate-batch-size 不是预领数量。线程池、模型和媒体参数不在此次派发迁移中顺带变更。

## 10. 切换与回滚

采用短维护窗口、分阶段切换，不同时让两套派发器竞争同一批任务。

1. 增量迁移字段与索引；历史任务标记 KAFKA，旧服务继续可读。
2. 发布支持显式后端归属的代码，先保持 Kafka 模式。旧领取入口和新领取入口都必须校验 dispatch_backend，不能仅在候选查询中过滤。
3. 暂停创建/手动重试入口，停止 Outbox 新投递；尽量等待在途任务自然结束。
4. 若必须中止，撤销旧执行权并等待实际工作收尾；停止所有旧 Worker，确认不会有旧进程继续续租。未知模型调用单独列出，不能直接算作可重跑任务。
5. 备份并核对所有非终态任务、owner、代次和 Outbox。对租约无效且符合迁移条件的任务设置 DATABASE 和允许领取时间；未知结果设置隔离标记。
6. 对迁移后的分析执行 Outbox 停止派发，保留历史审计记录，不直接删除表；已在 Kafka 中的旧消息不可再取得 DATABASE 任务执行权。
7. 启动一个数据库模式 Worker，确认领取、续租、完成、故障恢复正常；API 切换为只写 DATABASE 任务，恢复入口。
8. 验证后清理分析相关 Kafka Bean、依赖、配置和 Docker 服务。若其他业务仍使用 Kafka，基础设施不能一并删除。

回滚同样先停止新领取、处理在途任务，禁止直接启动旧版 Worker 混跑。只对未终态且确认可安全恢复的任务改变归属，并按任务 ID + 业务代次幂等生成执行 Outbox。终态不重投，未知结果继续隔离；恢复旧入口后再开放提交。

过渡期需要兼容后端归属校验的新旧适配版本；不支持该字段的历史二进制不能作为混合运行的回滚版本。

## 11. 观测与验收

主要指标：待领取数量、最老任务等待时长、领取竞争失败次数、领取成功到业务启动延迟、活跃视频数、租约续期失败、自动恢复次数、隔离任务数、提交到完成耗时、片段排队和模型调用失败。

日志关联 taskId、executionNo、owner、stage 和错误分类；禁止输出签名 URL、密钥或完整敏感请求。

必须验证：

1. API 不依赖 Kafka 也能创建任务并返回；重启后数据库任务可被领取。
2. 两个真实 MySQL 连接或两个 Worker 竞争同一任务，仅一个领取成功；不可只用 Mock 或 H2 替代并发验收。
3. 提交超过本地容量，不会超领或无限进入内存队列。
4. 领取后崩溃、提交拒绝、领取提交结果未知，均存在确定恢复路径。
5. 续租失败、租约过期、owner 替换后，旧写入被数据库拒绝。
6. 成功响应已保存时恢复不重复调用模型；未知调用不自动重发。
7. 取消和手动重试与领取并发时，旧代次不能启动或写入新结果。
8. 恢复失败不会每秒重复触发昂贵操作，预算与隔离跨进程重启保留。
9. 终态持久化后缓存/通知失败，不重新分析。
10. Kafka 完全不可用时数据库模式仍能启动并完成主链路，不能残留 KafkaTemplate 必需注入或消费者启动依赖。
11. 队列、租约、线程池和进程实际退出之间没有许可泄漏或提前释放。
12. 保持现有片段模型重试、原始响应复用、解析和持久化测试通过。

## 12. 分阶段执行计划

### P0：派发解耦与数据库准备

补充调度字段、索引与增量脚本；引入后端开关和领取归属校验；将 TaskProcessor 输入、完成事件与 Kafka 解耦。验收：新旧模式能独立装配，旧路径行为未意外改变。

### P1：数据库领取和容量管理

实现 CAS 领取、视频容量许可、提交失败清理和租约登记。先用模拟处理器验证多实例竞争与崩溃窗口。验收：任务不超领、无重复有效 owner、无本地许可泄漏。

### P2：接入现有流水线与恢复策略

连接 TaskProcessor，保留执行权传播；实现协调失败延期和结果未知隔离。验收：已保存产物复用、迟到写入拦截、模型调用重试边界不变。

### P3：API 接入与完整链路验收

调整上传确认、手动重试、压测入口和缓存流程；使用真实 MySQL、模拟模型完成故障矩阵，再做小量真实视频验证。验收：无 Kafka 依赖也能完整执行。

### P4：切换与清理

按维护窗口迁移在途任务，停止旧投递与消费；清理无用途依赖、配置和文档，更新项目展示页与面试材料。压测历史可保留，但标明对应旧架构。

## 13. 本方案的取舍

数据库调度不能提高模型本身的处理能力，积压只是改由任务表承载。它需要正确的索引、容量控制、租约和恢复策略，但当前规模下比同时协调 Kafka 位点和数据库任务状态更直接。

保留项目真正有价值的能力：大文件可靠上传、阶段产物复用、共享片段池、有限模型重试、执行权校验与可恢复结果。移除的是当前收益有限的派发协调复杂度。
