# 视频分析架构轻量化方案

2026-09-10 · 设计稿，替代此前兼容迁移方案。当前只修改文档，未删除代码、服务或数据。

## 1. 结论

采用数据库任务表 + 后台领取，不保留 Kafka 派发、任务 Outbox、双后端开关与历史兼容流程。

创建任务只修改同一个 MySQL 数据库中的业务记录，可以用一个本地事务完成。后台查询已提交任务并原子领取，不存在“必须同时提交任务和发出消息”的双写要求，因此分析任务 Outbox 没有必要。

模型 API 和对象存储仍是外部副作用，不能用 MySQL 事务一起回滚。这些问题通过响应保存、有限重试、写入保护和失败处理解决，不再用 Outbox 包装整条链路。

设计优先级：代码路径清楚 > 自动恢复程度高。允许进程故障中的视频明确失败、用户重试；不为了自动接续每一种中间状态再造复杂任务调度系统。

## 2. 目标架构

```text
API：鉴权 / 上传 / 创建任务 / 查询 / 取消 / 用户重试
                        ↓ 本地事务
                     MySQL
                        ↑ 扫描 + CAS领取
Worker：TaskScheduler → 视频业务池 → VideoAnalysisService
                                      ↓
                      下载 → ASR → 候选区间 → 裁剪
                                      ↓
                         RAG参考 → 共享片段池
                                      ↓
                           模型调用 → 保存片段结果
```

保留 API 与 Worker 的进程分工：重启耗时分析服务不影响上传与查询。不为减少模块数量而把媒体处理放入 HTTP 线程。

## 3. 直接删除什么

| 删除项 | 理由 |
|---|---|
| TaskConsumer、DeadLetterConsumer、KafkaListenerConfig | 不再消费分析消息 |
| AsyncConsumerSupervisor、AsyncVideoCoordinator | 无消费者生命周期、分区撤销和 ACK 需要协调 |
| 分析 TaskMessage、死信/重试 Topic 与消息配置 | 执行直接读取数据库任务 |
| TaskOutboxService、TaskOutbox、Mapper、状态枚举及执行 Outbox 表 | 无任务与消息双写 |
| OutboxDispatcherScheduler、OutboxRecoveryScheduler、相关配置 | 数据库任务本身就是待执行记录 |
| TaskProcessor.sendTaskEvent 与 KafkaTemplate | 当前源码仅找到事件发送，未找到该完成事件的消费入口；前端继续查询任务 |
| Kafka / ZooKeeper / Kafka UI 本项目专用容器和依赖 | 实施时全仓确认无剩余用途后移除 |
| dispatch_backend、双运行模式、灰度切换与旧消息回滚逻辑 | 用户不要求兼容旧部署或旧数据 |
| 原 DIRECT_VIDEO 分支和兼容分析模式判断 | 产品统一为语音筛选后的片段分析 |
| 为 Kafka 重投设计的消息代次比较与 ACK 布尔返回值 | 新执行入口不存在消息新旧判断 |
| QUEUED、DEAD 等历史队列状态 | 状态直接表达业务执行 |
| 新方案上一版的 recovery_count、next_dispatch_at、dispatch_hold 和通用恢复决策器 | 第一版不实现整局自动故障接管，避免新增调度状态机 |

上传确认、手动重试和压测入口必须同步移除 Outbox 调用。接口返回与前端状态映射一起调整。旧 Kafka 测试从默认构建移除；实验报告可以保留为历史材料，不再作为当前架构说明。

## 4. 合并什么

建议只保留三类主干职责，不强制拆成更多服务：

1. **TaskScheduler**：扫描、预留本地容量、调用领取、提交业务线程、注册运行上下文、续租、超期任务处理。定时扫描和续租分开调度，不在定时线程里执行视频分析。
2. **TaskRepository**：候选查询、CAS 领取、续租、受保护状态/结果写入。可以由 Service + Mapper 实现，不另加空泛的仓储接口体系。
3. **VideoAnalysisService**：合并 TaskProcessor 与 AudioPrefilterPipeline，按顺序编排媒体、ASR、文本筛选、RAG、片段分析，返回明确业务结果。

保留 FFmpeg、ASR、文本筛选、对象存储、RAG 等领域能力组件，避免把全部代码塞进一个大类。

片段层保留协调器和有界池的职责区分。已有 SegmentAnalysisExecutor 如果复杂度可控可直接使用；允许删除为废弃路径提供的分支，不以“必须复用”为限制，也不为换类名而重写经过测试的取消逻辑。

## 5. 最小状态与数据

父任务状态统一为：

```text
PENDING → RUNNING → SUCCEEDED / PARTIAL / FAILED
PENDING 或 RUNNING → CANCELLED
FAILED 或 PARTIAL → 用户重试 → PENDING
```

阶段使用独立 stage 字段：下载、音频准备、转写、筛选、裁剪、分析。去掉估算百分比，前端展示阶段与已完成片段数。

核心调度字段：task_id、status、attempt_no、owner_token、lease_until、created_at、started_at、finished_at、error_code/error_message。

- attempt_no：用户重试时增加，用于区分结果和片段记录；不再使用语义含混的 retry_count。
- owner_token：每次成功领取生成 UUID，阻止失效执行者写入。
- lease_until：DB 时间判断有效性。
- 不需要另外保存 worker_id 才能保证正确性；实例标识可用于日志。

建议索引：(status, created_at, task_id) 与 (status, lease_until, task_id)。最终用实际查询计划验证。

只保留一套执行历史载体：父任务保存当前运行信息，片段记录以 task_id + attempt_no + segment_no 唯一标识；阶段产物引用及当前配置放在统一 manifest 中。若需要独立 attempt 表保存配置/产物历史，则不再在多张表重复保存同一份阶段状态。最终表结构以字段用途清单评审决定，不机械保留旧表。

ASR requestId、模型原始响应引用、结果和必要用量证据仍有价值；删除的是通用阶段调度状态，不是这些业务数据。

## 6. 领取：只领取真正能开始的任务

每个 Worker 初始视频并发为 3，使用本地 Semaphore 预留位置。扫描每秒一次，先 tryAcquire，拿不到位置就不查询待领取任务。

```text
预留一个本地位置
→ 查询最早的 PENDING 候选
→ CAS：PENDING 改 RUNNING，设置 owner 和 90秒租约
→ 提交视频线程
→ 实际退出后归还位置
```

SQL 示意：

```sql
UPDATE analysis_task
SET status = 'RUNNING', owner_token = :owner,
    lease_until = TIMESTAMPADD(SECOND, 90, NOW(3)),
    started_at = NOW(3)
WHERE task_id = :id AND attempt_no = :attempt
  AND status = 'PENDING';
```

只有更新一行才执行。多 Worker 读到同一候选没有问题；竞争失败有限尝试其他候选或退出本轮，不忙等。

提交线程池被拒绝且确定业务从未启动时，按 owner 条件退回 PENDING；释放失败由超期清理收尾。领取提交结果未知时不开始业务，等待核对或超期，不冒险重复调用。

视频池不承担积压：本地许可覆盖提交中和执行中的任务，排队主体留在数据库。允许极小线程池队列处理线程退出瞬间的交接，不允许依据队列容量超领任务。

## 7. 续租和故障：保留必要可靠性，删掉自动接管复杂度

保留 90 秒租约、约 20 秒续租起点。独立维护线程只为本实例登记且有效的执行续租，不要求任务“每完成一步”才续。

条件写入必须校验 owner、attempt、RUNNING 和未过期租约。子结果写入需在短事务中锁定并校验父行，再写子表，防止取消/失效检查和真正写入之间的竞态。不持锁做媒体或模型调用。

**与上一稿的重大变化：租约过期不自动重新运行整局。**

- 后台用条件更新将过期 RUNNING 标为 FAILED，原因 EXECUTION_INTERRUPTED，保留已保存片段与响应。
- 清理更新包含原 owner、attempt、租约过期和 RUNNING 条件，不能覆盖刚续租或已完成的任务。
- 超期清理只调整数据库状态；不能凭它归还旧进程中仍在运行的线程容量。
- 旧线程即使返回，也因 owner/状态/有效期不符而不能覆盖结果。
- 用户可查看失败原因和已保存结果，再主动重试。

这是明确的产品取舍：待处理任务不会因 Worker 重启丢失；执行中的任务可能失败，需要用户重试。它不提供所有阶段自动续跑，但流程更简单，不会以恢复名义无条件重复付费调用。

若未来真实运营需要进程崩溃自动续跑，再按证据增加可恢复阶段，而不是现在一次性覆盖全部故障窗口。

## 8. 片段并发、失败和重试

保留“视频父线程 + 共享片段池”。它们分别承担整局编排和片段并发，有实际隔离价值，不属于重复线程池。

- 片段先记录，再提交；成功、失败分开保存，最终父任务按结果写 SUCCEEDED/PARTIAL/FAILED。
- 模型调用内部最多尝试 3 次，有限退避、抖动、重新限速；响应保存和解析不进入调用重试循环。
- 不可重试错误直接记录，其他片段继续处理。
- CountDownLatch 统计实际退出，不把 Future.cancel 当成任务已停。
- 取消和续租失败禁止新调用及写入，协作式中断等待；外部调用的实际停止仍受 SDK 与网络超时影响。
- 若本地片段未退出，不应无限接受后续任务堆积在被占满的片段池；保留收尾登记和容量保护，超出收尾期限告警并停止该执行槽继续派发。

用户重试增加 attempt_no，清理旧 owner，只复用同一输入和同一分析配置下明确成功的片段。第一版不自动复用各种 PROCESSING 中间状态；需要再次调用的片段，应向用户说明会重新执行。已绑定原始响应的解析恢复可作为明确、独立的操作保留。

## 9. 还可以删减的横向复杂度

| 项目 | 建议 |
|---|---|
| 任务详情 Redis 缓存 | 第一版去掉，直接查 MySQL，减少数据库状态与缓存失效协调；Redis 仍可用于现有鉴权/限流等实际用途 |
| 任务完成 Kafka 事件 | 当前无消费入口，删除；前端继续轮询 |
| 多 Provider 的旧直传兼容层 | 删除主链路不用的旧门面；保留一个小的模型接口与实际使用的实现即可 |
| 各阶段多份 JSON/数据库状态 | 建立字段用途表，合并重复清单与状态；保存一个权威清单和必要引用 |
| 显式业务参数传递与 ThreadLocal 重叠 | 选择统一 RunContext(taskId, attempt, owner, cancellation)；减少相同状态在多处绑定，不能漏掉片段线程传播 |
| RAG 与独立评估工具 | 与视频调度无直接关系，不为了轻量化删除用户需要的领域检索能力 |
| 通用长任务调度框架、事件总线、恢复策略接口层级 | 当前不引入 |

不把所有检查都删除：所有权校验、容量限制、取消、失败结果保存与可观测性仍是正确性要求。

## 10. 实施顺序

1. 定稿业务状态、数据库字段、故障后失败需用户重试的语义；不沿用旧消息字段名。
2. 实现新任务创建、CAS领取、续租、过期失败清理；用模拟业务验证正确性。
3. 合并业务编排，接入媒体/RAG/片段链路；调整用户重试与取消。
4. 删除 Kafka / Outbox、旧模式和无订阅方事件；清理强制 Bean 注入及构建依赖。
5. 更新 schema、接口、前端阶段展示、启动配置与项目文档。
6. 在全新测试库验证完整链路，再切换开发运行环境。不做历史数据兼容迁移；“不需兼容”不等于本次文档评审已授权清空现有数据库。

## 11. 验收标准

- Kafka 不运行、相关依赖移除后，API 与 Worker 可正常启动并完成视频分析。
- 使用真实 MySQL 多连接竞争，保证同任务只领取一次；本地视频执行不超过许可数量。
- API 事务回滚不会出现可执行任务；Worker 重启能领取原先 PENDING。
- 领取后崩溃最终进入明确失败，不永远 RUNNING；旧线程不能覆盖新结果。
- 续租与过期清理、完成与取消、领取与用户操作的竞态均有条件更新验证。
- 片段失败不吞掉其他成功结果；模型重试、不可重试、中断和保存失败均验证。
- 任务详情无需缓存也可准确展示阶段、片段结果和中断原因。
- 无默认入口仍引用 Outbox、旧 TaskMessage、Kafka ACK 或 DIRECT_VIDEO。
- 指标只保留必要项：最老排队时间、运行数、领取/续租失败、过期失败、片段成功率与任务总耗时。

## 12. 需要明确接受的边界

轻量化后：数据库任务不会因为内存任务丢失而消失，但进程故障中的视频不会全部自动续跑；过期任务明确失败，由用户重试。模型是否已在远端执行仍可能未知，不能保证零重复计费。

这条边界是换取删除通用自动恢复调度器的前提。如果必须做到无人介入恢复，则应重新加入有证据的恢复机制，而不是在现有简化方案中隐式承诺。
