# Apex Legends Wiki RAG 数据集

> 当前实验范围已收敛为 PC 英雄玩法知识。`data/legends` 只保留 28 位英雄的玩法与
> 技能信息，不包含 Mobile、背景故事、皮肤和通用说明。正文统一为简体中文；英文
> 规范名只保留在元数据和技能名括注中，用于实体对齐与溯源。

基于 [Apex Legends Wiki](https://apexlegends.fandom.com/wiki/Apex_Legends_Wiki)（Fandom MediaWiki）通过 API 采集，用于 RAG（检索增强生成）场景。

## 使用方式

### 整理与翻译

```powershell
# 从原始抓取结果中只保留 PC 英雄玩法信息
python scripts/curate_pc_legend_data.py --apply

# 使用百炼文本模型转换为简体中文；已完成文件会自动跳过
$env:DASHSCOPE_API_KEY = "your-key"
python scripts/translate_legend_data_zh.py

# 旧数据曾缺失玩法概览时，从原始 Git 版本确定性恢复
python scripts/restore_legend_gameplay_zh.py --apply

# 检查 28 张名单和 zh-CN 门禁，不写数据库
python scripts/import_rag_data.py --dry-run
```

`import_rag_data.py` 默认只读取 `data/legends`。名单不完整、混入非 PC 英雄或任一
文件未声明 `language: zh-CN` 时，导入会直接拒绝执行。

### 当前检索基线

旧语料时代的评测集不再参与参数选择。当前保留两层冻结题集：

- `eval/legend_zh_bench_v1.jsonl`：基础回归集，确认显式英雄名与技能问题不发生退化；
- `eval/legend_zh_player_hard_v1.jsonl`：玩家困难集，用实战语境、俗称、现象反推、机制组合和
  近域范围外问题进行首轮方案筛选；
- `eval/legend_zh_player_hard_v2.jsonl`：当前扩量集，每位英雄 3 条正例，用于后续检索方案与
  阈值选择。v1 原样保留在 v2 前 40 条中，保证历史结果可复现。

每次报告都记录数据集 SHA-256，避免不同实验误用不同题集。默认命令仍运行基础回归集；
涉及阈值或检索策略选择时，两层题集必须分别报告，不能用基础集高分掩盖困难集问题。

```powershell
python scripts/rag_eval.py --label legend-zh-bench

python scripts/rag_eval.py `
  --dataset rag-data/eval/legend_zh_player_hard_v1.jsonl `
  --label legend-zh-player-hard
```

评测脚本默认 `K=3`，与线上 `final-top-k=3` 保持一致；需要做候选池实验时必须显式传入
`--k` 并在实验记录中注明，不能把不同 K 的 Precision 直接比较。

管理员检索测试接口会同时返回 `rawCandidates → scorePassedCandidates → diversifiedCandidates
→ selectedCandidates → hits` 五个阶段。评测脚本基于同一次请求的原始候选离线扫描阈值，
默认范围为 `0.45～0.75`、步长 `0.01`，不需要为每个阈值重复调用 Embedding：

```powershell
python scripts/rag_eval.py --label threshold-sweep-v1 `
  --threshold-start 0.45 --threshold-end 0.75 --threshold-step 0.01
```

扫描给出的 `pareto_candidates` 只用于展示召回与拒答之间的非支配候选，不能直接替业务
选择权重；最终阈值仍需在未参与调参的测试集上确认。

#### 首轮阈值实验（2026-09-01）

固定 `candidateTopK=20`、`finalTopK=3`、`maxChunksPerCard=2` 和当前索引，只调整
`minScore`。36 条中文 bench 的完整链路结果如下：

| minScore | Entity Hit@1 | Section Hit@3 | 无答案拒绝率 | 无答案误召回率 |
|---:|---:|---:|---:|---:|
| 0.61 | 100% | 96.43% | 75% | 25% |
| 0.62 | 100% | 96.43% | 87.5% | 12.5% |
| 0.63（离线模拟） | 100% | 92.86% | 100% | 0% |

因此当前默认值更新为 `0.62`。`0.63` 虽能拒绝全部负例，但会额外丢失“地平线大招”的
正确 Section，不作为默认值。剩余误召回是“世界边缘”被匹配到“变幻”，下一步应优先做
英雄知识域的查询路由，而不是继续抬高全局阈值。

#### 首轮切片大小实验（2026-09-01）

固定 28 张 PC 英雄卡、36 条中文 bench、`candidateTopK=20`、`finalTopK=3`、
`maxChunksPerCard=2` 和 `minScore=0.62`，只改变
`targetChars/minChars/maxChars/overlapChars`。两个候选方案都写入独立 Milvus collection，
未回写 MySQL，也未替换当前基准索引；每组完整链路连续运行 3 次。

| 方案 | 切片参数 | 向量数 | Entity Hit@1 | Section Hit@3 | 无答案拒绝率 | 平均上下文字符 | 平均 P50 / P95 |
|---|---|---:|---:|---:|---:|---:|---:|
| 小切片 | 450 / 300 / 600 / 80 | 281 | 100% | 92.86% | 100% | 771.00 | 254.00 / 323.67 ms |
| 当前基准 | 650 / 400 / 800 / 100 | 223 | 100% | 96.43% | 87.5% | 943.00 | 264.67 / 369.33 ms |
| 大切片 | 850 / 500 / 1000 / 120 | 192 | 100% | 92.86% | 100% | 956.69 | 258.67 / 309.00 ms |

小切片使向量数增加 26.0%，并把平均注入上下文减少 18.2%；大切片使向量数减少
13.9%，但平均上下文略增。两个候选方案都消除了“世界边缘”的误召回，同时都让
“地平线黑洞”的相关片段落到 `0.62` 以下，Section Hit@3 因此下降 3.57 个百分点。
这说明切片变化会改变相似度分数分布，不能沿用阈值后只看单个指标。

本轮不提升候选索引，继续保留 650 / 400 / 800 / 100 基准。下一轮应先扩充困难正例和
范围外负例，再分别扫描各索引的阈值；英雄知识域路由完成后，再判断小切片节省上下文的
收益能否覆盖分区召回损失。延迟数据未做独占压测和预热控制，仅作工程参考，不作为本轮
选择依据。

#### 首轮混合检索实验（2026-09-02）

固定当前 650 / 400 / 800 / 100 索引、`minScore=0.62` 和同一套 36 条 bench，比较纯
向量、BM25 与向量并行召回后等权 RRF、BM25 只重排语义候选三种链路。BM25 基于 MySQL
中的 223 个现有 chunk 构建内存索引，中文使用二元字词，标题与标题路径分别提高权重；
RRF 使用 `k=60`，向量与词法权重均为 1.0。每组完整链路连续运行 3 次。

| 方案 | Entity Hit@1 | Section Hit@3 | Section Precision@3 | 无答案拒绝率 | 平均上下文字符 | 平均 P50 / P95 |
|---|---:|---:|---:|---:|---:|---:|
| 纯向量 | 100% | 96.43% | 79.17% | 87.5% | 943.00 | 256.67 / 327.00 ms |
| BM25 并集 + RRF | 100% | 96.43% | 52.38% | 87.5% | 1423.97 | 268.67 / 366.67 ms |
| BM25 只重排 + RRF | 100% | 96.43% | 79.17% | 87.5% | 955.56 | 259.00 / 320.33 ms |

并行并集没有增加命中，却引入大量只有词面重合的候选，使 Section Precision 下降 26.79
个百分点、平均上下文增加 51.0%。只重排能够消除这部分污染，但没有超过纯向量基准，
不同词法权重的离线扫描也没有提高 Entity Hit、Section Hit 或拒答率。

当前 bench 的正例都包含明确英雄名，中文别名增强后纯向量已经全部排到 Entity Top1；
唯一 Section 漏项来自飞雀语料只有“技能”总标题，而不是排序错误，因此 BM25 无法修复。
本轮保持 `hybrid-retrieval-enabled=false`，不把混合检索提升到默认链路。实验代码保留为关闭
状态，后续只有在加入缩写、数值、专有名词等真正适合词法检索的困难集后才重新评估；即使
重新开启，也默认只重排语义候选，不允许纯 BM25 候选直接进入上下文。

#### 玩家困难集复测（2026-09-02）

新增 `legend_zh_player_hard_v1.jsonl`，共 40 条：28 条正例覆盖 28 位英雄，12 条负例与英雄
知识处于同一游戏语境，但实际询问武器数值、地图路线、赛季规则、外设设置、阵容推荐等未入
库信息。正例不再直接问“某技能有什么效果”，而是从玩家看到的现象和决策反推知识，例如：

- “门已经被踹没，只剩空门框，催化姬还能不能重新封住”；
- “电妹吃一个大招加速剂为什么直接灌满，而且一格能放两个”；
- “地图刚冒出新盒子，艾许如何追刚打赢的队”。

每条正例的 `relevant_titles` 与 `relevant_sections` 都已对照 28 张现有 Markdown 卡片校验，
没有用知识库之外的游戏常识充当标准答案。固定 650 / 400 / 800 / 100 索引、TopK=3、
`minScore=0.62`，纯向量与“BM25 只重排语义候选”各运行 3 次：

| 方案 | Entity Hit@1 | Hit@3 | Section Hit@3 | Section Precision@3 | MRR | 拒答率 | 平均上下文字符 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 纯向量 | 92.86% | 96.43% | 89.29% | 62.50% | 0.9464 | 100% | 879.20 |
| BM25 只重排 + RRF | 96.43% | 96.43% | 89.29% | 60.71% | 0.9643 | 100% | 885.05 |

混合重排将沃特森“天才火花”从第二位提到第一位，Entity Hit@1 提升 3.57 个百分点，MRR
提升 0.0179；代价是 Section Precision@3 下降 1.79 个百分点。这个提升来自真实的排序修正：
纯向量把“催化姬英雄升级”排在 0.6582，略高于
“沃特森 > 天才火花”的 0.6549；BM25 利用“大招加速剂、一格两个、护盾恢复”等词面证据，
将正确片段排到第一位。

腐蚀“100 点研究点”问题仍被拒绝。其正确实体已在向量候选前两位，BM25 也把“实地研究”
排到第一，但最高向量分只有 0.6127，未达到 0.62 的语义门槛。这不是召回或融合失败，而是
阈值取舍。将阈值临时降至 0.60 后，28 条正例全部 Entity Top1，但“小帮手配装与伤害”成为
误召回，负例拒答率由 100% 降为 91.67%。因此暂不下调阈值。

困难集证明上一轮“混合检索完全无提升”主要受基础题天花板影响，但当前收益仍只有 1/28 条
正例，样本量不足以直接把混合链路设为默认。下一步需要继续增加不出现规范英雄名的玩家原话、
英文缩写和数值问题，并用独立测试集验证这 3.57 个百分点不是对当前 40 条题的偶然拟合。

#### 玩家困难集扩量复测（2026-09-02）

在不修改 v1 的前提下新增 `legend_zh_player_hard_v2.jsonl`，从 40 条扩展到 120 条：

- 84 条正例：28 位英雄各 3 条，尽量覆盖战术、被动和终极技能，而不是对同一技能换词复述；
- 36 条负例：新增投掷物、配件、制造、地图资源、毒圈、赛事、网络、录像、账号、匹配、
  身法和任务规则等近域问题；
- v1 的 40 条数据逐行原样保留为 v2 前缀；
- 无重复 ID、无重复问题，归一化文本相似度大于等于 0.82 的近重复数量为 0；
- 28 位英雄正例数全部为 3，所有金标标题和章节均能在当前 Markdown 卡片中找到。

固定当前 650 / 400 / 800 / 100 索引、`minScore=0.62`、TopK=3，完成一轮真实 API 初筛：

| 方案 | Entity Hit@1 | Hit@3 | Section Hit@3 | Section Precision@3 | MRR | 拒答率 | 平均上下文字符 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 纯向量 | 90.48% | 92.86% | 79.76% | 56.15% | 0.9107 | 91.67% | 878.80 |
| BM25 只重排 + RRF | 91.67% | 92.86% | 79.76% | 55.75% | 0.9167 | 91.67% | 897.61 |

扩量后，BM25 仍然只修复沃特森“天才火花”这一条：Entity Hit@1 提升 1/84，即 1.19 个
百分点；Hit@3、Section Hit@3 和拒答率没有提升，Section Precision@3 下降 0.40 个百分点，
平均上下文增加 18.81 字符。因此 40 条集上的 3.57 个百分点提升是真实排序修正，但不是广泛
收益，继续保持混合检索默认关闭。

v2 还暴露了更有价值的失败类型：腐蚀“实地研究”、催化姬“暗影帷幕”、腐蚀毒气罐、
万蒂奇回声、沃特森拦截信标和恶灵传送门等问题，正确知识要么已在原始候选中但低于 0.62，
要么被语义相近的救援、护盾、墙体片段压制；BM25 对这类不使用规范技能名的场景描述帮助有限。
36 条负例中，手雷伤害、蹬墙身法和键位配置被误召回为英雄技能，说明下一阶段应优先评估
知识域路由、分类型阈值或更强的语义重排，而不是继续扩大纯词法候选并集。

#### HeadingPath 消融与 BM25 补召回实验（2026-09-02）

为了验证“把标题路径编码进向量后，是否已经吸收了部分词法检索能力”，新增
`embedding-heading-path-enabled` 开关。关闭时只从 Embedding 文本中移除 `Section:
{headingPath}`，Milvus 元数据和 MySQL 中的 `heading_path`、原始正文、切片参数均保持不变。
实验使用独立的 223 向量影子集合，不覆盖当前基准集合，也不回写 MySQL。

固定 v2 的 120 条题、650 / 400 / 800 / 100 切片、`minScore=0.62`、候选 Top20、最终 Top3
和每卡最多 2 个 chunk，完成一轮真实 API 初筛：

| 方案 | Entity Hit@1 | Hit@3 | Section Hit@3 | Section Precision@3 | MRR | 拒答率 | 平均上下文字符 |
|---|---:|---:|---:|---:|---:|---:|---:|
| HeadingPath 入向量，纯向量基准 | 90.48% | 92.86% | 79.76% | 56.15% | 0.9107 | 91.67% | 878.80 |
| HeadingPath 不入向量，纯向量 | 92.86% | 94.05% | 84.52% | 57.94% | 0.9345 | 91.67% | 918.91 |
| HeadingPath 不入向量，BM25 并集 + 等权 RRF | 94.05% | 97.62% | 84.52% | 39.68% | 0.9464 | 91.67% | 1337.41 |

去掉 HeadingPath 后，纯向量并未退化，反而新增召回腐蚀“研究点”和万蒂奇“回声跳跃”，
只丢失直布罗陀“轰炸”；Entity Hit@1、Hit@3 和 Section Hit@3 分别提升 2.38、1.19 和
4.76 个百分点。这说明当前长标题路径不一定总是有效特征，也可能稀释正文语义。该结论目前
仅是一轮单题集初筛，不能据此永久删除 HeadingPath，后续应重复运行并在独立测试集验证。

在同一个无 HeadingPath 向量库上允许纯 BM25 候选进入并集后，BM25 补回催化姬“暗影帷幕”、
直布罗陀“轰炸”和沃特森“拦截信标”3 条漏召回，并将艾瑟儿无人机问题从第二位提升到第一位，
Hit@3 提升 3.57 个百分点；36 条负例的误召回数量没有增加。但是 Section Hit@3 的新增与退化
互相抵消，净提升为 0，Section Precision@3 下降 18.26 个百分点，平均上下文增加 45.54%。
因此 BM25 的“补召回”价值已经得到验证，但当前等权 RRF 并集不适合直接作为最终上下文：
下一轮应只针对语义漏召回启用词法候选，或增加更严格的融合后过滤，再比较补回率与污染率。

根据后续决策，无 HeadingPath 方案已提升为当前默认纯向量索引：
`apex_knowledge_chunk_experiment_no_heading_v1`。`heading_path` 仍保存在 Milvus 与 MySQL 元数据中，
用于结果展示、章节判定和后续去重，只是不再拼接进 Embedding 文本；混合检索继续默认关闭。
保留 HeadingPath 的原基准集合不删除，便于回滚和复现实验。

#### 条件式 BM25 补位实验（2026-09-02）

全量 BM25 并集虽然补回 3 条正例，但污染和上下文膨胀明显，因此继续在同一个无
HeadingPath 影子索引上验证“只补空位、不重排向量结果”。触发顺序为：

1. 向量候选先经过 `minScore=0.62`、每卡最多 2 个 chunk 和 Top3 截断；
2. 只有至少 1 个向量候选通过门槛、但最终不足 3 个时才查询 BM25；
3. 已有向量结果顺序保持不变，BM25 只在末尾补空位；
4. 查询没有任何向量候选通过 0.62 时不启动补位，继续拒答。

首轮“补满 Top3”会在 120 条题中的 61 条触发 BM25，并补回直布罗陀“防御轰炸”和
沃特森“拦截信标”两条正例。它没有增加负例误召回，但平均上下文仍比纯向量增加 40.22%，
说明仅限制触发时机还不够。

随后对候选增加两层约束：每次最多补 1 个 chunk；候选必须已经位于向量 Top20，且向量分数
不低于宽松门槛 0.60。离线扫描 0.50～0.61 后，0.60 与更低门槛能保留相同的有效新增召回，
但预计接纳的补位 chunk 明显更少，因此用 0.60 完成真实 API 复测：

| 方案 | Entity Hit@1 | Hit@3 | Section Hit@3 | Section Precision@3 | MRR | 拒答率 | 平均上下文字符 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 无 HeadingPath，纯向量 | 92.86% | 94.05% | 84.52% | 57.94% | 0.9345 | 91.67% | 918.91 |
| 无 HeadingPath，BM25 全量并集 + RRF | 94.05% | 97.62% | 84.52% | 39.68% | 0.9464 | 91.67% | 1337.41 |
| 条件补满 Top3，无候选语义下限 | 92.86% | 96.43% | 86.90% | 40.87% | 0.9425 | 91.67% | 1288.48 |

保守方案仍在 61 条题上执行内存 BM25 查询，但最终只有 18 条接纳补位，其中正例 16 条、

当前结论是：候选级宽松语义门槛和单 chunk 上限能明显控制 BM25 污染，优于全量并集；但
1/84 的收益仍不足以把它设为默认。代码以默认关闭的实验开关保留，下一步应使用未参与本轮
门槛选择的独立测试集，验证直布罗陀这一收益是否可泛化，再决定是否启用。

#### 多证据配额与上下文预算实验（2026-09-02）

过去的题集只要求命中一个英雄或章节，不能回答“每个英雄最多 2 块会不会漏掉复合问题”。
本轮新增 `legend_multi_evidence_v1.jsonl`，为每条题显式标注 3 个必须出现的“英雄 + 章节”
证据：8 条题同时询问单个英雄的被动、战术和终极技能，4 条题要求组合 3 位英雄完成防守
重整、侦察链、转点或区域封锁。指标改为：

- 必需证据覆盖率：3 个金标证据中实际召回的比例；
- 必需证据完整命中率：一条题的 3 个证据是否全部找齐；
- 必需证据 Precision：找回的金标证据数 / 实际返回 chunk 数。

第一组固定无 HeadingPath 影子索引、纯向量、`minScore=0.62`、候选 Top20、最终 Top3、
上下文上限 3500，只改变每张英雄卡最多返回的 chunk 数：

| 每卡上限 | 必需证据覆盖率@3 | 完整命中率@3 | 证据 Precision@3 | 平均上下文字符 |
|---:|---:|---:|---:|---:|
| 1 | 38.89% | 0% | 48.61% | 1584.08 |
| 2 | 47.22% | 0% | 51.39% | 1729.50 |
| 3 | 55.56% | 8.33% | 56.94% | 1726.67 |

只看 8 条单英雄复合题时，每卡 2 块到 3 块使证据覆盖率从 45.83% 提升到 58.33%，并首次
完整找齐 1/8 条题，平均上下文反而基本不变。这证明固定上限 2 确实会截掉有效的第三块，
不能作为所有查询的硬规则。但 4 条跨英雄题在上限 1、2、3 时覆盖率都为 50%，说明这类题
的主要问题不是每卡配额，而是 Top3 容量和候选排序；跨英雄查询应优先保证实体多样性。

第二组固定每卡最多 3 块、最终 Top6，只改变上下文字符预算：

| 字符上限 | 必需证据覆盖率@6 | 完整命中率@6 | 证据 Precision@6 | 平均实际字符 | 平均返回块数 |
|---:|---:|---:|---:|---:|---:|
| 1500 | 41.67% | 0% | 51.39% | 1335.25 | 2.42 |
| 2500 | 55.56% | 8.33% | 48.75% | 2047.08 | 3.58 |
| 3500 | 63.89% | 16.67% | 43.19% | 2603.42 | 4.67 |
| 6000 | 63.89% | 16.67% | 39.58% | 2890.08 | 5.08 |

1500 明显过紧；3500 到 6000 已不再增加覆盖率或完整命中率，只会继续增加上下文并降低
证据密度，因此当前 3500 字符预算有实验依据，不需要无限放宽。Top3 扩到 Top6 时，整体
证据覆盖率从 55.56% 提升到 63.89%，跨英雄题从 50% 提升到 75%，但单英雄题仍停在
58.33%。后者说明剩余漏召回来自正确技能块没有进入高分候选，而不是上下文上限；继续增大
TopK 无法替代查询拆解、技能意图识别或 rerank。

本轮结论不是把全局配置直接改成“每卡 3 块 + Top6”，而是为后续自适应策略提供边界：
简单单事实问题继续使用较小上下文；识别到单英雄多技能问题时允许同卡最多 3 块；识别到
跨英雄组合问题时降低单卡配额并扩大总 TopK。当前只有 12 条定向题，结果用于证明机制和
选择预算拐点，正式上线前仍需扩充独立测试集，并加入最终答案事实正确率评测。

#### Top6 全量困难集复测（2026-09-02）

为了确认 Top6 是否适合直接替换线上 Top3，使用包含 84 条单事实正例和 36 条近域负例的
`legend_zh_player_hard_v2.jsonl` 重新完成三组真实 API 对照。固定 HeadingPath 基准索引、
纯向量、`minScore=0.62` 和 3500 字符上限：

| 方案 | Hit@K | Section Hit@K | Section Precision@K | 拒答率 | 平均上下文字符 | P95 上下文字符 |
|---|---:|---:|---:|---:|---:|---:|
| Top3，每卡最多 2 块 | 92.86% | 79.76% | 56.15% | 91.67% | 878.80 | 1789 |
| Top6，每卡最多 2 块 | 92.86% | 79.76% | 55.34% | 91.67% | 920.72 | 2054 |
| Top6，每卡最多 3 块 | 92.86% | 83.33% | 46.67% | 91.67% | 1186.45 | 2539 |

只把 Top3 改成 Top6 没有补回任何实体或正确章节，平均上下文增加 4.77%。Top6 配合每卡
3 块后新增 3/84 条正确章节，Section Hit 提升 3.57 个百分点，但平均上下文比基准增加
35.01%，Section Precision 下降 9.48 个百分点。新增的催化姬“穿刺尖刺”、幻象“派对主角”
和纽卡斯尔“移动护盾”前面都存在两个相同 HeadingPath 的重叠 chunk；正确章节实际是同英雄
的第三块，因此此前被每卡上限 2 截断。

基于同一次 API 返回的原始 Top20 候选继续做离线消融：先按 `cardCode + headingPath` 去重，
再执行每卡最多 2 块和 Top3，Hit@3、拒答率保持 92.86%、91.67% 不变，Section Hit@3 从
79.76% 提升到 84.52%。它补回上述 3 条外，还补回罗芭“鉴宝之眼”，并且 Top6 在去重后

配额；相比全局扩大 TopK，更优先的改进应是检索后按章节去重或引入 MMR 多样化。

因此当前不把 Top6 设为全局默认值。Top6 在 12 条多证据复合题上仍有价值，后续可作为复杂
查询的自适应上限；普通单事实问题继续 Top3，并先验证章节去重对多证据集和最终答案质量的
影响。离线去重结果不等同于线上完整链路结果，正式修改前必须实现去重并复跑两套题集。

### 重新采集

```bash
cd rag-data
pip install requests beautifulsoup4
python scraper.py
```

采集脚本特点：
- 从 28 个根分类递归发现页面
- 使用 MediaWiki `parse` API 获取完整 HTML 渲染内容
- BeautifulSoup 清洗 HTML → 纯文本
- 5 线程并发，自动限速
- 自动跳过图片/音频/皮肤等非文本子分类

### 采集原理

```
根分类 (28个)
  └→ 递归发现子分类（跳过图片/音频类）
       └→ 收集所有页面 ID
            └→ action=parse API 获取完整 HTML（并发 x5）
                 └→ BeautifulSoup 清洗（去导航/样式/脚本）
                      └→ 输出 Markdown + JSONL
```

## 数据质量说明

- **parse API vs explaintext**：使用 `action=parse` 而非 `action=query&prop=extracts`，内容量提升 2.5 倍（英雄页面提升 6 倍），因为 parse API 会完整渲染 Infobox、表格等结构化数据
- **短页面**：少量 Event/Map 页面在原 wiki 上即为 stub（<500 字符），这是数据源本身的特性
- **分类准确度**：基于页面标题 + 所属分类关键词自动归类，偶有边界情况（如角色武器页可能归入 weapons）
- **外链图片**：图片和外部链接已剔除，只保留纯文本内容
