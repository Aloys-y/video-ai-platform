# DoVideoAI 面试版项目梳理

> 这份文档不是“架构大全”，而是帮你把 `简历-DoVideoAI.md` 里的项目讲得更稳，更贴近当前代码实现。

## 1. 30 秒版本

DoVideoAI 是一个“上传视频 -> 异步分析 -> 返回结果”的 AI 视频分析平台。系统拆成 `video-api` 和 `video-worker` 两个 Spring Boot 服务：

- `video-api` 负责鉴权、限流、分片上传、创建任务。
- `video-worker` 负责消费 Kafka、调用多模态模型、回写任务结果。

这个项目真正要解决的，不是“调一下 AI 接口”，而是 3 个工程问题：

1. 大文件上传如何支持断点续传和秒传。
2. AI 调用耗时长且不稳定，如何异步化、幂等化、可重试。
3. 多用户并发下，如何避免重复处理、资源冲突和系统被打爆。

## 2. 面试时建议的讲述顺序

按这个顺序讲，基本 3 到 5 分钟能说清：

1. 先讲架构拆分。`video-api` 处理用户请求，`video-worker` 处理长耗时 AI 任务，中间用 Kafka 解耦。
2. 再讲上传链路。前端做分片和采样哈希，后端用上传会话、分布式锁和 S3 兼容 Multipart Upload 保证续传和合并。
3. 再讲异步任务。任务先落库，再发 Kafka，Worker 用状态机和条件更新保证幂等。
4. 最后主动承认边界。现在代码能跑，但在越权、消息一致性、成本统计、告警补偿上还没有做到生产级。

## 3. 简历里最稳的说法

- 可以说：系统拆成 API 服务和 Worker 服务，核心链路是“上传服务”和“异步分析服务”解耦。
- 可以说：上传用的是前端分片 + 服务端 Multipart Upload，不是本地磁盘 merge。
- 可以说：分片状态主要落 MySQL，Redis 主要做进度缓存和限流，不要说“Redis 维护分片状态”。
- 可以说：任务状态靠状态机 + `UPDATE ... WHERE status = ?` 实现天然幂等。
- 可以说：AI 厂商通过 `AiVideoProvider` 抽象，支持 DashScope、Zhipu、OpenAI-compatible 切换。
- 可以说：当前代码实现了全局限流和用户级限流。

## 4. 面试官最容易追问的点

| 面试点 | 你可以怎么答 |
| --- | --- |
| 为什么拆 `video-api` 和 `video-worker` | 因为上传和鉴权是低延迟请求，AI 分析是长耗时任务，两者资源模型完全不同，需要独立扩缩容和故障隔离。 |
| 断点续传怎么做 | 先创建 `upload_session`，记录 `uploadId`、`totalChunks`、`uploaded_chunks`，已传分片存在 MySQL JSON 字段里。 |
| 秒传怎么做 | 客户端先算文件指纹，`/upload/init` 阶段按 `fileHash` 查已有上传会话，命中 `MERGED` 直接复用。 |
| 为什么说任务是幂等的 | Worker 抢任务时不是直接改状态，而是带旧状态条件更新，只有一个实例能成功从 `PENDING -> QUEUED -> PROCESSING`。 |
| AI 切换怎么做 | 不是在业务里写一堆 `if-else`，而是 `AiVideoProvider` 接口 + `@ConditionalOnProperty`。 |
| 现在离生产还差什么 | 越权校验、消息最终一致性、配额扣减、调用日志、告警补偿、密钥治理，这几个都还要补。 |

## 5. 核心实现拆解

### 5.1 上传链路：前端分片，后端会话化

前端当前默认是固定 `5MB` 分片、`3` 并发，并且会把默认值传给后端；真正生效的分片大小以后端 `init` 返回值为准，这样前后端不会漂移。

```js
const Upload = {
  DEFAULT_CHUNK_SIZE: 5 * 1024 * 1024,
  CONCURRENCY: 3,
  ...
  const requestedChunkSize = this.DEFAULT_CHUNK_SIZE;
  const fileHash = await this.computeFileHash(file);
  const initResult = await Api.post('/upload/init', {
    fileName: file.name,
    fileSize: file.size,
    chunkSize: requestedChunkSize,
    fileHash: fileHash,
  });
  this.state.chunkSize = initResult.chunkSize || requestedChunkSize;
}
```

出处：`frontend/js/upload.js:15-16`, `frontend/js/upload.js:107-117`

后端初始化上传时，会先做文件类型和大小校验，再按 `fileHash` 命中“秒传”或“断点续传”。

```java
if (request.getFileHash() != null) {
    UploadSession existing = uploadSessionMapper.selectByFileHash(request.getFileHash());
    if (existing != null) {
        if (existing.getStatusEnum() == UploadStatus.MERGED) {
            return UploadInitResponse.builder()
                    .uploadId(existing.getUploadId())
                    .instantUpload(true)
                    .build();
        }
        if (existing.getStatusEnum() == UploadStatus.UPLOADING) {
            return UploadInitResponse.builder()
                    .uploadId(existing.getUploadId())
                    .chunkSize(existing.getChunkSize())
                    .totalChunks(existing.getTotalChunks())
                    .uploadedChunks(existing.getUploadedChunkIndexList())
                    .instantUpload(false)
                    .build();
        }
    }
}
```

出处：`video-api/src/main/java/com/videoai/api/service/UploadService.java:85-108`

这里面真正的关键不是“分片顺序”，而是“同一个分片不要被重复上传，同一份上传元数据不要被并发写乱”。当前做法是：

1. 用 `uploadId + chunkIndex` 作为锁粒度，只锁同一分片，不锁整次上传。
2. 拿到分布式锁后再查一次数据库，做双重检查，避免重复重试或多标签页续传时同一分片被重复上传。
3. 上传成功后，用 MySQL JSON 原子追加已传分片索引，避免元数据和对象存储状态竞争。

```java
boolean locked = lock.tryLock(5, 30, TimeUnit.SECONDS);
session = uploadSessionMapper.selectByUploadId(uploadId);
if (session.isChunkUploaded(chunkIndex)) {
    return buildProgressResponse(session);
}
storageService.uploadPart(videoPath, b2UploadId, partNumber,
        file.getInputStream(), file.getSize());
uploadSessionMapper.appendUploadedChunk(uploadId, chunkIndex);
```


上传完成后，服务端走的是 S3 兼容 Multipart Upload 的 `completeMultipartUpload`，不是本地文件拼接。


你可以把这一段总结成一句话：

“上传链路的核心不是 Multipart 本身，而是上传会话、同一分片去重和并发安全；分布式锁主要防的是重复上传和元数据竞争，不是保证全局分片顺序。”

### 5.2 异步任务：任务先落库，再投 Kafka

用户不是一上传完就立即调 AI，而是先确认提示词，再创建分析任务。

```java
AnalysisTask task = new AnalysisTask();
task.setTaskId(IdGenerator.generateTaskId());
task.setUploadId(uploadId);
task.setUserId(userId);
task.setVideoUrl(storagePath);
task.setPrompt(prompt);
task.setStatusEnum(TaskStatus.PENDING);
analysisTaskMapper.insert(task);

kafkaTemplate.send(TopicConstant.TASK_TOPIC, task.getTaskId(), buildTaskMessage(task));
```

出处：`video-api/src/main/java/com/videoai/api/service/UploadService.java:351-387`

这一步的价值有两个：

- API 服务响应更快，不会被 AI 接口阻塞。
- 后台处理可以独立扩容，Worker 挂了也不影响上传接口。

但要注意，当前代码是“先写 DB，再发消息”，这也埋下了后面会讲的一致性问题。

### 5.3 幂等和状态机：核心不是枚举，而是条件更新

真正保证“同一个任务不会被多个 Worker 重复处理”的，不是 `enum` 本身，而是数据库条件更新。

```java
if (currentStatus == TaskStatus.PENDING) {
    int rows = analysisTaskMapper.updateStatusWithCheck(
            taskId, TaskStatus.PENDING.getCode(), TaskStatus.QUEUED.getCode());
    if (rows == 0) {
        return;
    }
}

int started = analysisTaskMapper.startProcessing(taskId);
if (started == 0) {
    return;
}
```

出处：`video-worker/src/main/java/com/videoai/worker/processor/TaskProcessor.java:66-83`

对应的状态机定义也很清楚：

```java
case PENDING -> target == QUEUED || target == CANCELLED;
case QUEUED -> target == PROCESSING || target == CANCELLED;
case PROCESSING -> target == COMPLETED || target == FAILED || target == CANCELLED;
case FAILED -> target == RETRYING || target == DEAD;
case RETRYING -> target == PROCESSING || target == FAILED || target == DEAD;
```

出处：`video-common/src/main/java/com/videoai/common/enums/TaskStatus.java:83-89`

面试里可以直接讲：

“我们不是靠 Java 锁保证幂等，而是靠状态机 + `WHERE old_status = ?` 让 DB 自己做仲裁。”

### 5.4 失败重试：重试逻辑在任务层，不在 AI SDK 层

当前项目的失败处理逻辑，真实位置在 `TaskProcessor.handleFailure()`，不是 `AiService` 里本地 `sleep` 三次。

```java
analysisTaskMapper.failTask(taskId, errorMessage);

if (task.canRetry()) {
    analysisTaskMapper.incrementRetry(taskId);
    kafkaTemplate.send(TopicConstant.TASK_TOPIC, taskId, retryMsg);
    sendTaskEvent(taskId, "RETRYING", errorMessage);
} else {
    analysisTaskMapper.markAsDead(taskId, errorMessage);
    kafkaTemplate.send(TopicConstant.DEAD_LETTER_TOPIC, taskId, Map.of(...));
    sendTaskEvent(taskId, "DEAD", errorMessage);
}
```

出处：`video-worker/src/main/java/com/videoai/worker/processor/TaskProcessor.java:182-225`

消费者本身也是手动 ack：

```java
try {
    taskProcessor.process(message);
} catch (Exception e) {
    log.error("Task consumer error: taskId={}", taskId, e);
} finally {
    ack.acknowledge();
}
```

出处：`video-worker/src/main/java/com/videoai/worker/consumer/TaskConsumer.java:43-50`

这套逻辑的真实含义是：

- Kafka 不负责你的业务重试。
- 业务失败后，是应用自己把任务重新发回 Topic。
- 超过最大次数后，再进入死信队列。

## 6. 当前代码和常见简历话术的差异

这部分建议你面试前自己先改口，不然很容易被问穿。

| 容易说过头的地方 | 当前代码里的真实情况 |
| --- | --- |
| Redis 维护分片状态 | 分片状态在 `upload_session.uploaded_chunks`，Redis 只缓存进度。 |
| 文件秒传基于 MD5 | 前端现在算的是“采样 SHA-256”，DTO 也允许 32 位或 64 位哈希。 |
| 用 MinIO Compose API 合并 | 当前实现是 S3 兼容 `Multipart Upload + CompleteMultipartUpload`。 |
| AiService 内做指数退避重试 | 当前重试主要在 `TaskProcessor.handleFailure()` 里通过 Kafka 重投实现。 |
| 已经实现三级限流 | 当前只有全局限流和用户级限流两层。 |
| AI 返回结构化 JSON | 当前 `AiService` 的系统提示词要求返回 Markdown，不是结构化 JSON。 |

## 7. 代码里值得主动承认的生产问题

下面这些点，不是为了否定项目，而是你在面试里主动说出来，反而显得你知道“能跑”和“可上线”的差距。

### 7.1 越权风险比较明显

`/task/{taskId}` 查询详情时，没有按 `userId` 做归属校验。上传相关接口也有类似问题。

- `TaskController.getTask()` 直接按 `taskId` 查：`video-api/src/main/java/com/videoai/api/controller/TaskController.java:27-30`
- `TaskService.getTask()` 也只按 `taskId` 查：`video-api/src/main/java/com/videoai/api/service/TaskService.java:45-75`
- `UploadService.getStatus()`、`uploadChunk()`、`completeUpload()`、`submitTask()` 都没有校验当前用户是不是上传会话 owner：`video-api/src/main/java/com/videoai/api/service/UploadService.java:154-217`, `:223-316`

影响：

- 只要知道别人的 `taskId` 或 `uploadId`，理论上就可能读到、续传、完成或提交别人的任务。

建议：

- Service 层统一带 `currentUserId` 参数。
- 所有查询和更新都加 `user_id = ?` 条件。

### 7.2 DB 和 Kafka 之间没有最终一致性保障

任务是先写库，再发消息：

- 插入任务：`video-api/src/main/java/com/videoai/api/service/UploadService.java:351-363`
- 发送消息：`video-api/src/main/java/com/videoai/api/service/UploadService.java:365-370`

问题在于：

- 如果 `insert` 成功、`send` 失败，数据库里会留下一个 `PENDING` 任务。
- 日志里写了 “Task will be picked up later”，但项目里并没有补偿扫描器或 outbox。

证据：

- 代码里没有 `@Scheduled` 扫描待补发任务。
- 只有一句日志：`video-api/src/main/java/com/videoai/api/service/UploadService.java:369`

建议：

- 上事务消息 / outbox pattern。
- 或至少做定时补偿，把长期 `PENDING` 的任务重新投递。

### 7.3 API Key 实际上只是单 Key，不是 Key + Secret

`User` 表里有 `api_secret`，`UserService` 也会生成并 BCrypt 存储，但鉴权时只校验 `apiKey`：

```java
User user = userMapper.selectByApiKey(apiKey);
```

出处：`video-api/src/main/java/com/videoai/api/interceptor/AuthInterceptor.java:103-123`,
`video-infrastructure/src/main/java/com/videoai/infra/mysql/mapper/UserMapper.java:24-25`

影响：

- 当前更像“Bearer Key”，不是带签名的开放平台鉴权。

建议：

- 如果要做开放 API，应该上 HMAC 签名、时间戳、nonce、防重放。

### 7.4 配额和成本表已经建了，但运行时没真正用起来

库里有 `user_quota`、`ai_call_log` 表，错误码里也有配额相关定义，但实际业务没打通。

- 表结构：`sql/schema.sql:100-134`
- `completeTask()` 写结果时 `tokensUsed` 直接传 `0L`：`video-worker/src/main/java/com/videoai/worker/processor/TaskProcessor.java:122-127`
- 代码里基本没有 `user_quota`、`ai_call_log` 的使用逻辑

影响：

- 现在还谈不上真正的“成本控制”。
- 用户可以不断创建任务，系统不会按日/月配额做拦截。

建议：

- 创建任务前预扣配额。
- 回写模型实际 token 用量和调用时延。
- 失败时做配额回滚。

### 7.5 死信和重试还比较初级

当前失败任务会自己重投 Kafka，超限后进死信；但死信消费者只是打印日志。

- 应用层重试：`video-worker/src/main/java/com/videoai/worker/processor/TaskProcessor.java:196-225`
- 死信消费者只有日志，没有告警和人工处理：`video-worker/src/main/java/com/videoai/worker/consumer/DeadLetterConsumer.java:29-40`

再往深一点看，`TaskConsumer` 最终一定会 `ack`：

- `video-worker/src/main/java/com/videoai/worker/consumer/TaskConsumer.java:43-50`

这意味着：

- 如果“业务失败后重投 Kafka”这一步自己也失败了，原消息仍然已经被 ack。
- 任务可能停在 `FAILED` 或 `RETRYING`，不会再自动恢复。

建议：

- 发送重试消息时做更强的兜底。
- 或者统一走 outbox，不直接在消费线程里二次投递。

### 7.6 安全配置有明显问题

`application-dev.yml` 里直接提交了数据库、Redis、Kafka、对象存储、OAuth、AI API 的敏感配置。

出处：

- `video-api/src/main/resources/application-dev.yml:6-8`, `:38-40`, `:72-82`
- `video-worker/src/main/resources/application-dev.yml:6-8`, `:17-19`, `:43-45`, `:54`, `:61`

影响：

- 这在真实项目里属于严重安全问题，应该立刻换密钥。

建议：

- 仓库只保留 `*.example`。
- 真实配置走环境变量、密钥中心或 CI/CD 注入。

### 7.7 结果格式和解析逻辑不一致

`AiService` 的系统提示词要求“返回纯 Markdown，不要返回 JSON”，但 `TaskProcessor.extractSummary()` 又在尝试按 `"summary"` 字段去截取内容。

- 提示词要求 Markdown：`video-worker/src/main/java/com/videoai/worker/service/AiService.java:27-61`
- 摘要提取按 JSON 文本截取：`video-worker/src/main/java/com/videoai/worker/processor/TaskProcessor.java:162-176`

影响：

- 大多数情况下提取不到真正的 `summary`，最后只是退化成“取前 200 个字符”。

建议：

- 要么统一让模型返回 JSON。
- 要么结果落库时就按 Markdown 处理，不要再按 JSON 解析。

### 7.8 还有几个小但真实的问题

- `UploadController.complete()` 变量名叫 `videoPath`，但实际返回的是 `uploadId`：`video-api/src/main/java/com/videoai/api/controller/UploadController.java:50-53`
- `ApiResponse` 里的 `traceId` 只在错误响应里生成，成功响应没有；而且它不是链路透传的 request id：`video-common/src/main/java/com/videoai/common/dto/response/ApiResponse.java:56-63`, `:81-115`
- `completeUpload()` 整个方法加了 `@Transactional`，中间还包含远程对象存储调用，事务边界偏大：`video-api/src/main/java/com/videoai/api/service/UploadService.java:222-260`

## 8. 面试时最后可以怎么收尾

你可以这样收：

“这个项目我觉得最大的价值，不是把 AI 接上去，而是把上传、异步处理、幂等和失败重试这些工程问题先打通了。它现在已经能跑通主链路，但如果要上生产，我会优先补 4 件事：归属校验、消息一致性、配额与成本、密钥与告警体系。” 

这句话通常会让面试官感觉你不是只会堆技术栈，而是知道系统真正缺什么。
